\chapter{Conclusion}
\label{ch:conclusion}

\section{Main Findings}
\label{sec:main_findings}

For type-1 and type-2 transforms the time is concentrated in one place. The
\texttt{execute} stage, which spreads the points, transforms the fine grid and
corrects for the kernel, takes the large majority of it; \texttt{setpts}, which
sorts the points, takes a smaller but non-negligible share; and \texttt{makeplan}
takes almost none. A type-3 transform divides its time differently, because the
inner plan it needs and its per-target correction factors are both built in
\texttt{setpts}. Every parameter studied here acts inside the first two of those
stages.


Each parameter moves the total, and there are two kinds of parameters. 
Four of them -- the upsampling factor,
the maximum subproblem size and the two bin dimensions -- reduce the cost of one
stage only by raising the cost of another, so the cost as a function of the
parameter is a sum of two opposing terms and the best value lies where they
balance rather than at either extreme. The remaining two do not balance two
stages against each other. Sorting is a binary choice, and it should be enabled
for any input of a realistic size. The synchronisation threshold is an integer
that may take any value, but the library compares it with the thread count and
nothing else, so all it selects is which of two implementations of the adding
stage is used: a critical section when the thread count does not exceed it, and
atomic updates when it does. Its effect is therefore a step rather than a
balance, and only its position relative to the thread count matters. Which side
of that step is faster reverses with the thread count itself: below roughly ten
threads the critical section wins, above it the atomic updates do.

Where those balance points lie is a property of the problem and of the machine,
not of the library, and the quantities that fix them are few. The point density
decides how large a region a subproblem's points cover, and so whether writing a
subgrid or filling it dominates. The requested tolerance affects the kernel width,
and with it both the work per point and the padding around every subgrid. The
dimension multiplies that padding along every axis. The thread count changes how
fraction of l3 cache each thread has and how many threads contend for memory at once. The
thresholds these produce are sharp and can be located with experiments: gathering
doubles in cost once the staging buffer outgrows a thread's share of the
second-level cache, which at $32$ bytes per point is $4096$ points in two
dimensions; the sort reaches its floor once its counter array fits in the
first-level cache; and spreading leaves its flat regime once the region a bin
covers no longer fits there. The distances involved are not small. For the
reference transform the constant the library selects for the subproblem size
costs $1.44$ times the best value measured, and the synchronisation choice,
worth nothing at that constant, is worth up to a third of the run time once the
subproblem size is tuned.

The behaviour therefore separates into a part that can be predicted and a part
that must be measured. What follows from the geometry of the grids is
predictable: the average size of the subgrid a given subproblem size and bin
shape produce is derived in closed form and matches measurement to within one
percent, and because the adding stage costs a fixed number of cycles per cell
written, that model predicts the cost of the stage for configurations never run.
The cost of spreading as a function of the upsampling factor is reproduced in
all three dimensions. What follows from the memory hierarchy is predictable only
in part: the position of each threshold follows from a cache size, but the cost
of crossing it does not, and the model of the FFT holds only for transforms
whose fine grid exceeds the last-level cache, below which a fixed per-call
overhead dominates.

\section{Answers to the Research Questions}
\label{sec:rq_answers}

\paragraph{RQ1: Which of FINUFFT's configuration parameters affect performance?}
Six of the options the library carries reach the stages in which the time is
spent, and all six change the execution time measurably, but not by comparable
amounts. Whether the points are sorted dominates every other effect; among
configurations that sort, the upsampling factor and the two bin dimensions
together account for almost all of the remaining variation, and the maximum
subproblem size and the synchronisation threshold for a few percent between
them. The two smallest shares are the least transferable of the five: both
parameters act only on the spreading stage, so their contribution to the total
falls as the FFT grows

\paragraph{RQ2: Through which mechanism does each of those parameters act, and
what fixes the point at which its trade-off balances?} 
Every parameter studied speeds up one stage and slows another, so each has an interior optimum. The upsampling factor trades spreading against the FFT: raising $\sigma$ narrows the kernel, making spreading cheaper, and enlarges the fine grid the FFT must transform (Chapter~\ref{ch:sigma_selection}). The maximum subproblem size trades gathering against adding (Chapter~\ref{ch:parameter_tuning}). Adding falls as subproblems grow, because the padding of every subgrid is paid once per subproblem; gathering rises once the per-thread staging buffer no longer fits in that thread's share of L2, because its writes then occupy line-fill buffers for a full memory round trip. The sort bin dimensions act on three stages through three quantities: the sort through the size of its per-thread counter array against L1, spreading through the padded region a bin covers against L1 and L2, and adding through the size of the subgrids the resulting point order produces. Where each balance lies depends on point density, which decides how large a region a subproblem's points cover; on the tolerance, which sets the kernel width and with it the padding; on dimension, which multiplies that padding along every axis; on the thread count, since gathering slows down only when many threads compete for memory; and on the cache sizes, which set the thresholds above.

\paragraph{RQ3: Which of those costs can be written in closed form accurately
enough to choose a value without measuring it?} Those that follow from the
geometry of the grids can. The subgrid a configuration produces is predicted to
within a percent, and with it the cost of the adding stage, which is
proportional to the cells written; the cost of spreading as a function of the
upsampling factor is reproduced in all three dimensions. Those that follow from
the memory hierarchy can be located but not evaluated: the value of a parameter
at which a working set leaves a cache level is given by the capacity of that
level, while the cost of crossing it is not, and must be measured once on the
machine. The model of the FFT cost is the weakest of the three, holding only
where the fine grid exceeds the last-level cache.

\section{Limitations}

The measurements throughout were taken on one machine, the Intel Xeon E5-2698 v4 of Section~\ref{sec:platform}, and the thresholds that turn out to matter most are expressed in terms of its cache sizes. The models are written in terms of those sizes rather than in absolute numbers, so they transfer in principle, but this was not verified on hardware with a different cache hierarchy, a different core count, or a memory system of a different bandwidth. Two of the mechanisms identified here depend on properties that vary more between machines than the cache sizes alone: the point at which gathering leaves the second-level cache depends on how many hardware threads share it, and the cost of memory contention at large subproblem sizes depends on the bandwidth available per thread.

The parameter search of Chapter~\ref{ch:parameter_importance} likewise covers a single workload; its ranking of the parameters is specific to that workload, and the analysis chapters show directly that a parameter which is insensitive at one density and thread count is decisive at another. The analyses concentrate on type-1 transforms in double precision, since that is the path the spreader takes; type-2 interpolation reuses the same subproblem structure but was not measured separately, and type~3 was not examined beyond the stage breakdown.

Two of the results also rest on a modified library rather than on FINUFFT as distributed. The dimensions of the sort bins are compile-time constants, so they were exposed as run-time options in order to be swept at all; a user of the released library cannot set them, and the gains attributed to them in Chapter~\ref{ch:parameter_importance} are therefore only available through a patch or a future release that exposes them. 
\section{Future Work}
\label{sec:future_work}

The natural continuation of this work is to turn the balance points into predictions. Each of the parameters studied here has a cost model with the right shape -- two opposing terms whose sum has an interior minimum -- but the constants that place that minimum are properties of the machine: the cost of a cache miss at each level, the effective bandwidth available to a thread, the overhead of a subproblem. An empirical model that calibrates these constants once per machine, from a short set of measurements at known configurations, could then predict the minimising parameter values for an arbitrary input from its density, dimension, tolerance and thread count, without a search. The evidence gathered here suggests this is achievable: the subgrid-size model already predicts the measured geometry to within a percent across a wide range of configurations, the cost of the adding stage is proportional to the number of cells written with a constant that does not vary, and the transitions in the spreading and sorting stages occur where the corresponding working set crosses a known cache boundary. What remains is to fit the machine-dependent constants that connect these quantities to time, and to validate the resulting predictions against a search of the kind performed in Chapter~\ref{ch:parameter_importance} across a range of inputs and machines.

A second, and prerequisite, line of work is a benchmark suite of transforms broad enough to measure whether such a model actually helps. The parameters studied here are chosen by heuristics, and a heuristic that improves the common case can quietly make some other case much worse: the search of Chapter~\ref{ch:parameter_importance} covered a single workload, and the analysis chapters show repeatedly that a parameter which barely matters at one density, dimension or thread count is decisive at another. A suite spanning those axes -- the three dimensions, densities from far below one point per cell to far above, tolerances across the usable range, single-threaded through fully-threaded, and both precisions -- run against the library defaults would give a baseline against which any proposed heuristic can be scored, reporting not only the mean improvement but the worst regression it causes. That second number is the one that matters for a library: a change that is faster on average and several times slower somewhere is not an improvement, and without a suite of this kind such a regression is only discovered by whoever runs into it.
