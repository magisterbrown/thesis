\chapter{Conclusion}
\label{ch:conclusion}

This chapter draws the results of the thesis together. It summarises the main
findings, answers the research questions posed in
Section~\ref{sec:research_questions}, compares the results with prior work,
states the limitations of the study, and outlines directions for future work.

\section{Main Findings}
\label{sec:main_findings}


Of all the parameters analysed, three left room to improve performance by replacing their default values with better ones: the upsampling factor, the maximum subproblem size and the bin dimensions. Changing any of them reduced the cost of one stage only by raising the cost of another, so each has a value at which the two costs balance. Expressing the cost as a function of the parameter allows that value to be found before the transform runs. The remaining two already had good default values. Sorting is a binary choice, and it should be enabled
for any input of a realistic size. The atomic-update threshold is an integer that the library compares with the thread count. It selects which of two implementations of the adding stage runs: a critical section when the thread count does not exceed it, atomic updates when it does. The default of $10$ appears to be a reasonable choice on this machine, because from about ten threads upwards spreading is limited by memory bandwidth rather than by the instructions it executes.

This thesis derived an accurate model to predict average subgrid size
assuming uniform distribution of points within one percent error.
That model allowed to estimate memory demand given different combinations of bin and subproblem sizes.
Besides subgrid size model amount of data in processing relative to l3 cache fraction. If data execedes 
that fraction model estiamtes number of cache misses. Miss do not grow sharply after some threshold, 
thats why model used log linear interpolation between of data relative to cache size to slowly increase amount
of misses.

The combinations of bin dimensions and maximum subproblem size chosen by this
procedure made the sort and spreading stages $1.29$ times faster on geometric
average over all test transforms and thread counts. The largest gain, $1.50$
times, was on $20$ threaded transforms with largest memory bandwidth demands. The
gains from the two parameters were also measured separately. Selecting $S_{\max}$
alone, with the bins left at their default, reduced the CPU time by only $4\%$,
so most of the gain came from the bin dimensions. In three dimensions, where no
bin larger than the default fits in the L1 data cache, the bins kept their
default size, and the whole gain of $6\%$ came from $S_{\max}$.

\section{Answers to the Research Questions}
\label{sec:rq_answers}

\paragraph{RQ1: Which of FINUFFT's configuration parameters affect performance
significantly on the machine under test?}
Sorting was the most significant parameter: disabling it made the transform an
order of magnitude or more slower. The upsampling factor was the next most
important, because it affects both the spreading and the FFT stages. The last
two, the bin dimensions and the maximum subproblem size, affect only the sort and
spreading. Of these, the bin dimensions mattered more. Both the Bayesian search
and the evaluation of the selection procedure agreed on this: the bin dimensions
accounted for more of the variance in the search, and for more of the gain when
the model was tested.

\paragraph{RQ2: Can models describe how changing each parameter affects the
cost of the individual stages of the transform?}
Yes, for the three parameters that trade the cost of one stage against another.
The upsampling factor affects the spreading and FFT stages, and both effects
were modelled. The cost of spreading depends on the kernel width: each point is
spread onto $w^d$ grid cells, and since the loop is vectorised, the number of
vector instructions is predictable and proportional to the time spent. The
upsampling factor also sets the input size of the FFT. The throughput of the
DUCC FFT grew with the transform size while the whole input fitted in cache;
beyond that, it fell as the $\mathcal{O}(\tilde{N} \log \tilde{N})$ bound
predicts.

The bin dimensions balance the sort against the spreading stage. Larger bins are
faster to sort into, but they increase the average size of the subgrid that
encloses a subproblem. As the total size of the subgrids grows, so does the
memory demand of the spreading stage, because every subgrid has to be added to
the fine grid, which for most transforms fits only in DRAM.

The maximum subproblem size sets the size of the staging buffer. When it is
small enough, the whole buffer fits in the thread's share of the cache. Very
small subproblems, however, create many subgrids, each surrounded by the same
padding, which creates the opposing overhead.

\paragraph{RQ3: Can such models choose a better configuration before a
transform runs?}
Yes, combinations of bin dimensions and maximum subproblem size can be ranked
before the transform starts. The model estimates the total number of memory
requests caused by writing back results and by spills out of cache during the
sort and the spreading stage, and keeps the combination that minimises them.
This approach accelerated the sort and the spreading stage by $29\%$ on
geometric average.

\section{Discussion}
\label{sec:discussion}

These findings are consistent with, and extend, the prior work reviewed in
Section~\ref{sec:related_work}. The trade-off behind the upsampling factor
agrees with what gNUFFTW~\cite{ou2017} found on a GPU: the best oversampling
ratio falls as the point density falls. gNUFFTW located that optimum by search,
whereas this thesis modelled the spreading side of it. gNUFFTW kept one
parameter fixed: the sector width of gpuNUFFT, which plays the role of both the
bin dimensions and $S_{\max}$ in a single value, and whose tuning it left for
future work. Yet in FINUFFT the corresponding parameters, above all the bin
dimensions, gave significant gains in the sort and spreading stages. The cache
limit on the padded bin appears to be the CPU counterpart of the shared-memory
limit that bounds the bins of cuFINUFFT~\cite{shih2021}, with the difference
that exceeding it makes spreading slower rather than impossible.

The results suggest a small but useful change to FINUFFT. The bin dimensions,
which carry most of the gain, are compile-time constants in the released
library; exposing them as options, or choosing them per transform, would
require little new code. Because the selection procedure evaluates only
closed-form expressions, it could run during planning without the cost of a
search, which makes it suitable even for transforms that are executed only once.
The benefit is largest for multithreaded transforms, where spreading is limited
by memory bandwidth, and smallest on few threads and in three dimensions.

\section{Limitations}
\label{sec:limitations}

All measurements were taken on one machine, the Intel Xeon E5-2698 v4 of
Section~\ref{sec:platform}. The models are written in terms of its cache sizes
rather than in absolute times, so they should transfer to other machines, but
this was not verified. The parameter search of
Chapter~\ref{ch:parameter_importance} covers a single type-1 workload, so its ranking
of the parameters is specific to that workload. 

The selection procedure also has limitations of its own. Its traffic estimate
assumes uniformly distributed points, which causes some slowdowns when the
points are clustered, as with the exponential distribution. The growth of cache
misses was estimated by log-linear interpolation between half and twice a
thread's share of the cache. This estimate gave good results on this processor,
but its ends may need to be adjusted on other machines.

\section{Future Work}
\label{sec:future_work}

The first continuation is to repeat the study on another machine, with a
different cache hierarchy, core count and memory bandwidth. This would test
whether the thresholds move where the models say they should, and whether the
selection procedure keeps its gains once its constants are refitted.

The second is a model for interpolation, the counterpart of spreading used by
type-2 transforms. Interpolation shares the bin sort, the bin dimensions and the
staging buffer with spreading, but each point reads its neighbourhood directly
from the fine grid, so there are no private subgrids and no adding stage. Its
traffic estimate would keep the terms of the sort and of the staging buffer and
replace the subgrid terms with reads of the fine grid. A model of interpolation
would also allow type-3 transforms to be tuned, since a type-3 transform consists
of a spreading step, as in type 1, followed by an inner type-2 transform.

\section{Closing Remarks}

Understanding why a configuration is fast has proven more useful than finding
it by search: it explains the defaults, shows where they fall short, and allows
better values to be chosen before a transform runs.
