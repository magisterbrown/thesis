\chapter{Conclusion}
\label{ch:conclusion}

This chapter draws the results of the thesis together. It summarises the main
findings, answers the research questions posed in
Section~\ref{sec:research_questions}, states the limitations of the study, and
outlines directions for future work.

\section{Main Findings}
\label{sec:main_findings}

For type-1 transforms the time is concentrated in one place. The
\texttt{execute} stage, which spreads the points, transforms the fine grid and
corrects for the kernel, takes the large majority of it; \texttt{setpts}, which
sorts the points, takes a smaller but non-negligible share; and \texttt{makeplan}
takes almost none. A type-3 transform divides its time differently, because the
inner plan it needs and its per-target correction factors are both built in
\texttt{setpts}. Every parameter studied here acts inside the first two of those
stages.


Each parameter moves the total, and there are two kinds of parameters. 
Four of them -- the upsampling factor, the maximum subproblem size and the two bin dimensions -- reduce the cost of one stage only by raising the cost of another. The cost as a function of such a parameter is a sum of two opposing terms, so the best value lies where they balance rather than at either extreme. The remaining two do not balance two
stages against each other. Sorting is a binary choice, and it should be enabled
for any input of a realistic size. The synchronisation threshold is an integer that may take any value, but the library compares it with the thread count and nothing else. All it selects is which of two implementations of the adding stage runs: a critical section when the thread count does not exceed it, atomic updates when it does. Its effect is therefore a step rather than a
balance, and only its position relative to the thread count matters.

Where those balance points lie is a property of the problem and of the machine,
not of the library, and the quantities that fix them are few. The point density
decides how large a region a subproblem's points cover, and so whether writing a
subgrid or filling the subproblem buffer with points dominates. The requested tolerance affects the kernel width,
and with it both the work per point and the padding around every subgrid. The
dimension multiplies that padding along every axis. The thread count changes the
fraction of the L3 cache each thread has and how many threads contend for memory at once. The thresholds these produce are sharp, and each can be located in advance. Gathering costs more once the staging buffer outgrows a thread's share of the last-level cache. The sort moves little beyond its compulsory traffic while its per-thread counter array fits in that same share, and spreading leaves its flat regime once the region a bin covers no longer fits in the first-level cache. The distances involved are not small. For the
reference transform the subproblem size the library selects moves $8.2$ lines
per point between the processor and memory in the spreading stage, against
$6.4$ at a value twelve times smaller, and over the $54$ test transforms the
sort takes $2.2$ times as long with the bins it fixes as with the selected ones.

The behaviour therefore separates into a part that can be predicted and a part
that must be measured. What follows from the geometry of the grids is predictable. The average size of the subgrid a given subproblem size and bin shape produce is derived in closed form and matches measurement to within one percent. The adding stage costs a fixed number of cycles per cell written, so that model also predicts the cost of the stage for configurations never run.
The cost of spreading as a function of the upsampling factor is reproduced in
all three dimensions. What follows from the memory hierarchy is predictable only in part. The position of each threshold follows from a cache size, but the cost of crossing it does not. The model of the FFT is narrower still, holding only for transforms whose fine grid exceeds the last-level cache; below that a fixed per-call overhead dominates.

For the spreader parameters the predictable part is enough to choose a configuration. A model of the memory traffic of the bin sort and the spreading stage, evaluated over the candidate bins and subproblem sizes that the cache limits allow, selects both parameters before the transform runs. On $20$ threads the selection is $1.49$ times faster than the library defaults on geometric mean over $54$ transforms and slower on only three. The larger bins make the sort $2.2$ times faster, and the selected subproblem size reduces the CPU time of the spreading stage by about $7\%$. For the upsampling factor no such procedure is proposed, because the FFT cost it would have to weigh can be ranked but not predicted.

\section{Answers to the Research Questions}
\label{sec:rq_answers}

\paragraph{RQ1: Which of FINUFFT's configuration parameters affect performance
significantly on the machine under test?}
Six of the options the library carries reach the stages in which the time is spent, and all six change the execution time of a transform: whether the nonuniform points are sorted (\texttt{spread\_sort}), the upsampling factor (\texttt{upsampfac}), the maximum number of points in a spreading subproblem (\texttt{spread\_max\_sp\_size}), the thread count above which the adding stage switches from a critical section to atomic updates (\texttt{spread\_nthr\_atomic}), and the dimensions of the boxes into which the points are sorted ($b_x$, $b_y$, $b_z$), which the released library fixes at compile time. Chapter~\ref{ch:parameter_importance} gives the share of the variation that each accounts for.

Four of the six speed up one stage and slow another, so each has an interior optimum; sorting and the synchronisation threshold select between alternatives instead. The upsampling factor trades spreading against the FFT: raising $\sigma$ narrows the kernel, making spreading cheaper, and enlarges the fine grid the FFT must transform (Chapter~\ref{ch:sigma_selection}). The maximum subproblem size trades gathering against adding: adding falls as subproblems grow, because the padding of every subgrid is paid once per subproblem, while gathering rises once the per-thread staging buffer no longer fits in that thread's share of L3. The bin dimensions act on three stages: the sort through the size of its per-thread counter array against that thread's share of L3, spreading through the padded region a bin covers against L1 and L2, and adding through the size of the subgrids the resulting point order produces (Chapter~\ref{ch:parameter_tuning}).

\paragraph{RQ2: Can models describe how changing each parameter affects the
cost of the individual stages of the transform?} For the upsampling factor, the
maximum subproblem size and the bin dimensions, yes, though not all to the same
degree. The subgrid a configuration produces is predicted to
within a percent, and with it the cost of the adding stage, which is
proportional to the cells written; the cost of spreading as a function of the
upsampling factor is reproduced in all three dimensions. The costs that follow from the memory hierarchy are located by thresholds, each given by the capacity of a cache level divided by the bytes a stage holds per unit of the parameter: the maximum subproblem size at which the staging buffer outgrows a thread's share of the last-level cache; the bin dimensions at which the counter array the sort keeps per thread outgrows that same share; and the bin dimensions at which the region a bin covers, padded by the kernel width, leaves the first-level cache. The first two enter a closed-form estimate of the DRAM lines the bin sort and the spreading stage move per point, through ramps whose ends are fitted once on the machine; over $360$ measured configurations its median error is $7\%$, and it ranks configurations better than it predicts their absolute traffic. The third is used as a hard limit on the bins rather than costed. Ranking is what choosing requires, and it holds wherever spreading is bound by bandwidth, which on this machine means from about ten threads upwards. The model of the FFT cost is the weakest, holding only
where the fine grid exceeds the last-level cache, so for the upsampling factor it ranks candidates but does not predict their cost.

Because the models are written in terms of the point density, tolerance, dimension, thread count and cache sizes rather than measured times, they are expected to carry over to other machines. This was not tested: all measurements were taken on one machine, and the fitted ramp ends would need to be measured again on another (Section~\ref{sec:limitations}).

\paragraph{RQ3: Can such models choose a better configuration before a
transform runs?} The models first show why there is room to improve on the
defaults. The default bins of
$16 \times 4$ cells leave a per-thread histogram of $2.85$\,MB on the reference
transform, against a $2.5$\,MB share of L3 on $20$ threads, so the sort is
already past its cache threshold; in one dimension the histogram runs to one or
two million counters and overflows every level of the cache. The default
$S_{\max} = 10^5$ moves $8.2$ lines per point between the processor and memory,
against $6.4$ at $S_{\max} = 8000$, where the stage is fastest. In three
dimensions, by contrast, even the default bin exceeds the first-level cache once
padded, so no larger bin is admissible and the procedure keeps it. The upsampling factor
heuristic considers only $1.25$ and $2$, although the balance between spreading
and the FFT often lies between them.

For the bin dimensions and the maximum subproblem size, the models also choose a
better configuration. The selection procedure of Chapter~\ref{ch:parameter_tuning}
uses only the dimension, precision, grid size, number of points, kernel width,
thread count and cache sizes, and takes well under a millisecond. On $20$ threads
it is faster than the defaults on $51$ of $54$ transforms and $1.50$ times faster
on geometric mean, with the largest gains in one dimension ($2.05$ to $2.15$
times) and the smallest in three ($1.08$ to $1.16$ times), where no bin larger
than the default fits in the first-level cache and only $S_{\max}$ changes. The
gains shrink with the thread count, to $1.23$ times on ten threads and $1.07$ on
one, because spreading is then limited by latency and computation rather than by
the traffic the model counts. With exponentially distributed points the procedure
is still $1.40$ times faster overall, but three-dimensional transforms become
slower in $15$ of $18$ cases. For the upsampling factor the question is left
open: its spreading cost is modelled accurately, but its FFT cost is not
predicted well enough to weigh against it.

\section{Limitations}
\label{sec:limitations}

The measurements throughout were taken on one machine, the Intel Xeon E5-2698 v4 of Section~\ref{sec:platform}, and the thresholds that turn out to matter most are expressed in terms of its cache sizes. The models are written in terms of those sizes rather than in absolute numbers, so they transfer in principle, but this was not verified on hardware with a different cache hierarchy, a different core count, or a memory system of a different bandwidth. Two of the mechanisms identified here depend on more than the cache sizes alone. The point at which the staging buffer leaves a thread's share of the last-level cache depends on how many threads share that cache, and the cost of memory contention at large subproblem sizes depends on the bandwidth available to each thread.

The parameter search of Chapter~\ref{ch:parameter_importance} likewise covers a single workload; its ranking of the parameters is specific to that workload, and the analysis chapters show directly that a parameter which is insensitive at one density and thread count is decisive at another. The analyses concentrate on type-1 transforms, mostly in double precision, since that is the path the spreader takes; type-2 interpolation reuses the same subproblem structure but was not measured separately, and type~3 was not examined beyond the stage breakdown.

Two of the results also rest on a modified library rather than on FINUFFT as distributed. The dimensions of the sort bins are compile-time constants, so they were exposed as run-time options in order to be swept at all. A user of the released library cannot set them, and the gains attributed to them in Chapter~\ref{ch:parameter_importance} are therefore available only through a patch, or through a future release that exposes them. The same holds for the selection procedure of Chapter~\ref{ch:parameter_tuning}, which chooses bin dimensions as well as $S_{\max}$.

The selection procedure has three limitations of its own. Its traffic estimate assumes uniformly distributed points, and with clustered points it fails in three dimensions, where it selects subproblems so large that each thread receives only a few of very different cost. It has no term for load imbalance at all, which is also the cause of its three slowdowns with uniform points. And the ramps that describe how traffic rises once a working set leaves its cache were fitted on this machine, so on another the procedure keeps its form but its constants would need to be measured again.
\section{Future Work}
\label{sec:future_work}

The first continuation is to repeat the study on another machine. The models
are written in terms of cache sizes and thread counts rather than absolute
times, but they were validated, and the ends of the ramps in the traffic
estimate were fitted, on a single processor. Repeating the measurements on one
with a different cache hierarchy, core count and memory bandwidth would test
whether the thresholds move where the models say they should, and whether the
selection procedure keeps its gains once its constants are refitted there.

The second is a model for interpolation, the counterpart of spreading used by
type-2 transforms and, through the inner transform it plans, by type-3
transforms. Interpolation shares the bin sort, the bin dimensions and the
staging buffer with spreading, but each point reads its neighbourhood directly
from the shared fine grid, so there are no private subgrids and no adding stage.
Its traffic estimate would therefore keep the terms of the sort and of the
staging buffer and replace the subgrid terms with the reads of the fine grid,
whose reuse is set by the region a bin covers. Whether the same thresholds
govern it, and whether a selection procedure built on such an estimate gains
as much as it does for spreading, remains to be measured.
