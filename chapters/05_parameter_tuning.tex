%\section{Overview}


This chapter turns to the two parameters of the spreader, the maximum subproblem size and the bin dimensions. It has two parts. First this chapter analyses how both parameters affect memory load during transform. Then it presetns a model that ranks combinations of these parameters to acieve highest throughput in the spreading stage.

\section{Parameters Under Consideration}

FINUFFT spreads the nonuniform points onto the uniform grid in two steps: the points are first sorted into bins, and then processed in batches, the subproblems. The maximum subproblem size sets how many points a batch may hold, and the bin dimensions set the size of the bins.

\section{Spreading Is Memory Bound}
\label{sec:memory_bound}

To find out what limits the spreading stage of the reference transform (Section~\ref{sec:workload}) was run with the library defaults at $1$ to $20$ threads and at all $40$ hardware threads, and two quantities were recorded over the spreading loop alone. The first is the traffic between the processor and main memory, read from the memory controllers' own counters of 64-byte line reads and writes; divided by the wall time of the loop it gives the DRAM bandwidth the stage consumes. The second is the number of instructions the threads retire per cycle (IPC), read from each thread's core counters around the gather, spread and add steps. Multiplied by the thread count, IPC becomes the instruction throughput of the whole processor. Each point is the median of three runs. Figure~\ref{fig:memory_bound} shows both quantities.

\begin{figure}[ht]
    \centering
    \includegraphics[width=0.85\textwidth]{figures/memory_bound/scaling.pdf}
    \caption{DRAM bandwidth consumed by the spreading stage (top) and instructions retired per cycle summed over all threads (bottom) for the reference transform, against the number of threads. The dotted line extends the throughput of one thread linearly; the shaded region uses both hardware threads of each core.}
    \label{fig:memory_bound}
\end{figure}

Figure~\ref{fig:memory_bound} shows that spreading scales almost linearly up to four threads. Beyond that it falls below linear scaling, and above ten threads its DRAM bandwidth saturates at about $30$\,GB/s, as the roofline model~\cite{williams2009roofline} predicts for a bandwidth-bound kernel. Between ten and twelve threads spreading becomes slower still. At that point the subgrid addition switches from a critical section to a lock-free algorithm~\cite[Sec.~3.7, p.~60]{herlihyshavit2012}, which guarantees system-wide progress regardless of how the threads are scheduled, but executes more instructions for every grid cell it updates.

Above about twelve threads, therefore, the spreading stage is memory bound: its time is set by how much data it moves between the processor and main memory, not by how many instructions it executes. The amount moved is not a fixed property of the transform. It grew from $4.0$ to $8.2$ lines per nonuniform point between one and twenty threads, because the share of the L3 cache available to each thread shrinks as threads are added. It also depends on how the configuration lays out the work. The subproblem size $S_{\max}$ fixes how large each subgrid and gather buffer is, and so whether they stay in cache. The bin dimensions fix the order of the points, and $\sigma$ fixes the size of the fine grid and the width of the kernel. Improving spreading on a machine whose cores are all in use therefore requires understanding how each of these parameters affects the memory demand of the stage.

\section{Subgrid size}
\label{sec:subgrid_size}
Sum of all subgrid sizes is a parameter that influences memory demand. A subgrid is a cuboid that wraps all the points assigned to its subproblem, padded by the kernel width. Subproblems themselves are picked from a partially bin-sorted array of points: rather than fully sorting all points by position, the points are only sorted into coarse bins, and each subproblem is then formed by taking a contiguous run of $S_{\max}$ points from this partially-sorted array. Because the points are randomly distributed, the subgrids of different subproblems sometimes overlap, so the sum of all subgrid areas exceeds the global area. Figure~\ref{fig:subgrid_overlap} shows how the first 20 such cuboids are written into the global grid, and how much they overlap one another along both axes. The rest of this section shows that the two parameters under consideration act on the subgrid in the same direction: increasing the bin size or decreasing $S_{\max}$ makes the sum of subgrids larger relative to the number of points they hold, so the stage zeroes and adds back more cells per nonuniform point. The add step reads and writes every subgrid cell's counterpart in the shared fine grid, and once the subgrids no longer fit in cache their own cells travel to and from memory as well, so a larger subgrid per point raises the bandwidth demand of the stage that Section~\ref{sec:memory_bound} identified as its limit.

\subsection{Estimating average subgrid size}

Average subgrid size, given uniform distribution of points can be estimated before transform based on the maximum subproblem size, the bin dimensions and the density. 1d subgrid size formula is the simplest to derive. Write $\tilde{N}$ for the number of cells of the fine grid, $\rho = M/\tilde{N}$ for the average number of points per cell, $b$ for the bin size in cells, and $w$ for the kernel width. Bin sorting places on average $\rho b$ points in each bin and orders the array by bin, but leaves the points within a bin in arbitrary order, so a subproblem built from a contiguous run of $S_{\max}$ points may draw them from anywhere inside the bins that run touches. Its bounding interval is therefore the union of those bins rather than the span of the points themselves. The run consumes $S_{\max} / (\rho b)$ bins worth of points and starts at an arbitrary offset inside the first of them, so it touches
\begin{equation}
    n_b = \frac{S_{\max}}{\rho b} + 1
    \label{eq:subgrid_bins}
\end{equation}
bins on average, covering $n_b b$ cells. FINUFFT then pads that interval by half a kernel width on each side, so that spreading needs no bounds checking, which adds a further $w$ cells. The average subgrid size in one dimension is thus
\begin{equation}
    L_1 = n_b b + w = \frac{S_{\max}}{\rho} + b + w.
    \label{eq:subgrid_1d}
\end{equation}
The three terms separate the three contributions: $S_{\max}/\rho$ is the extent the points genuinely occupy, $b$ is the slack introduced by sorting only into bins rather than fully, and $w$ is the kernel padding. 

In two dimensions the bins are visited $x$ fastest, so a contiguous run of points fills entire rows of bins along $x$ before advancing in $y$. A bin-row is $b_y$ cells tall, so a strip of it one cell wide holds $\rho b_y$ points and a subproblem reaches
\begin{equation}
    x_{\mathrm{ext}} = \frac{S_{\max}}{\rho\, b_y}, \qquad
    r = \frac{x_{\mathrm{ext}}}{N_x}, \qquad
    f = \min(1, r)
    \label{eq:subgrid_xext}
\end{equation}
cells along $x$ while it stays inside one row, where $r$ expresses that reach as a fraction of a bin-row and $f$ is the probability that the run does not fit inside a single row. Which of two shapes the subgrid takes depends on where the run happens to start; Figure~\ref{fig:subgrid_cuboid_examples} shows both. If it lies entirely within one row, as in Figure~\ref{fig:subgrid_cuboid_regular}, it is a compact box, $x_{\mathrm{ext}} + b_x$ cells wide and $b_y$ tall. If instead it straddles a row boundary, as in Figure~\ref{fig:subgrid_cuboid_wrapping}, it consists of a suffix of one row and a prefix of the next; those two pieces sit at opposite ends of the $x$ axis, so their common bounding box spans the full width of the grid and two rows in height, however few points the run holds. Figure~\ref{fig:subgrid_overlap} shows locations and dimensions of first 20 subgrids from a real transform: the compact subgrids tile each bin-row along $x$, while the straddling ones reach from edge to edge and are two rows tall. Averaging the two cases over the starting offset, and padding every extent by the kernel width, gives the mean subgrid area
\begin{equation}
    A_2 = (1 - f)\,(x_{\mathrm{ext}} + b_x + w)(b_y + w)
        \;+\; f\,(N_x + w)\bigl((\max(1, r) + 1)\, b_y + w\bigr).
    \label{eq:subgrid_2d}
\end{equation}

\begin{figure}[ht]
    \centering
    \includegraphics[width=\textwidth]{figures/subgrid_layout/subgrid_layout.pdf}
    \caption{Bounding boxes of the first 20 subgrids at $S_{\max}=2500$, coloured by whether the subproblem crosses a bin-row boundary.}
    \label{fig:subgrid_overlap}
\end{figure}
The first clamp, $f = \min(1, r)$ is a probability, and it saturates at one because a run longer than a row always spans the full width. The second clamp, $\max(1, r)$ is a row count, and it is floored at one because a straddling run covers two rows however short it is; for $r \geq 1$ the first term vanishes and the expression reduces to $(N_x + w)\bigl((r+1) b_y + w\bigr)$, the run starting at an arbitrary offset and therefore touching $r + 1$ rows on average.

In three dimensions the same construction applies once more, because the bins are visited $y$ next and $z$ slowest. A run now fills entire rows of bins along $x$ before advancing in $y$, and entire slabs of bins, meaning all bins sharing one $z$ index, before advancing in $z$. The reach along $x$ inside a single row becomes $x_{\mathrm{ext}} = S_{\max} / (\rho\, b_y b_z)$, and alongside $r$ and $f$ a second pair is needed for the slabs,
\begin{equation}
    q = \frac{S_{\max}}{\rho\, N_x N_y b_z} = r\,\frac{b_y}{N_y}, \qquad
    g = \min(1, q),
    \label{eq:subgrid_slab}
\end{equation}
where $q$ is the fraction of a slab a subproblem consumes and $g$ the probability that it crosses a slab boundary. Every subproblem then falls into exactly one of three cases, and since $q \leq r$ always, the probabilities partition cleanly: with probability $1 - f$ the run stays inside one row and its subgrid is compact; with probability $f - g$ it crosses a row boundary but not a slab boundary, so it spans the full width in $x$ while remaining a few rows tall; and with probability $g$ it crosses a slab boundary, whereupon the suffix and prefix it holds lie at opposite corners of an $x$--$y$ plane and the subgrid spans that plane entirely. Averaging over the three gives
\begin{equation}
    \begin{split}
    A_3 = {}& (1 - f)\,(x_{\mathrm{ext}} + b_x + w)(b_y + w)(b_z + w) \\
          &+ (f - g)\,(N_x + w)\bigl((\max(1, r) + 1)\, b_y + w\bigr)(b_z + w) \\
          &+ g\,(N_x + w)(N_y + w)\bigl((\max(1, q) + 1)\, b_z + w\bigr),
    \end{split}
    \label{eq:subgrid_3d}
\end{equation}

Each row averages every subgrid built during one transform, from $40$ subgrids at the largest subproblem size up to $20{,}000$ at the smallest. All three agree to within $1\%$, and the residual is largest at small $S_{\max}$, where the discrete number of bins a run touches is least well described by its average.

In three dimensions $b_z$ repeats the pattern one level up, by increasing size of bins that wrap along dimension 3, while keeping other bins proportional.

\section{Model of Memory Operations Based on the Maximum Subproblem Size}

During the spreading stage, nonuniform points are partitioned into spatially localised subproblems so that each subproblem's contribution to the fine grid can be accumulated independently. The parameter $S_{\max}$ (exposed in the FINUFFT interface as \texttt{spread\_max\_sp\_size}) sets an upper bound on the number of nonuniform points assigned to any single subproblem. It has two opposing effects in terms of memory demand.

The first factor is the size of the subgrids. Every subgrid must be zeroed before spreading and added to the fine grid afterwards, so each of its cells costs memory traffic. Section~\ref{sec:subgrid_size} showed that a subgrid is larger than the region its points occupy. This overhead can be measured as number of subgrid cells per subproblem, by calculating average subgrid size $A_d$ from Equations~\eqref{eq:subgrid_1d}, \eqref{eq:subgrid_2d} and~\eqref{eq:subgrid_3d}, dividing it by number of points in the subproblem $\frac{A_d}{S_{\max}}$. So every extra cell introduces overhead per point.

The second factor works in the opposite direction. Before spreading a subproblem, each thread copies the coordinates and strengths of its points into a staging buffer of size $(d+2)\,\texttt{sizeof(FLT)}\,S_{\max}$ bytes, a $d$ for each coordinate dimension and two complex strength of each point, so its size grows linearly with $S_{\max}$. While the buffer fits in the thread's share of the L3 cache, the lines written for one subproblem stay in cache untill the next one overwrites them. Once it no longer fits, buffer lines get evicted when gathering and must be fetched from a memory when a kernel processes them, so the gather step takes more cache misses and stalls. The same increase in $S_{\max}$ that makes the subgrid smaller per point therefore makes the gather miss more, and very large subgrids eventually leave the L3 cache as well. $S_{\max}$ trades memory traffic in the add step against memory traffic in the gather step.

The two effects can be put on one scale by estimating the number of DRAM lines (64 bytes) the spreading stage reads and writes per nonuniform point. Write $s = M / \max(n_{\mathrm{thr}}, \lceil M / S_{\max} \rceil)$ for the number of points in a subproblem, $A_d(s)$ for its mean subgrid size from Equations~\eqref{eq:subgrid_1d}, \eqref{eq:subgrid_2d} and~\eqref{eq:subgrid_3d}, and $\ell = 64 / (2 \cdot \texttt{sizeof(FLT)})$ for the number of complex cells in a line. Then
\begin{equation}
    \lambda = \frac{A_d(s)}{s\,\ell}, \qquad
    \beta = \frac{(d+2)\,\texttt{sizeof(FLT)}}{64}, \qquad
    u = \frac{1 - e^{-\rho\, w^{d-1} (w + \ell - 1)}}{\rho\, \ell}
    \label{eq:traffic_terms}
\end{equation}
are the total subgrid lines, the staging-buffer lines and the subgrid lines touched by the kernel, each per point; $u$ counts the lines covered by the $w^{d-1} \times (w + \ell - 1)$ footprint of a point's kernel, shared between points that fall close together. Whether the subgrid and the buffer stay in cache is modeled by log-linear interpolation between the size at which each starts to spill and the size at which it no longer fits at all,
\begin{equation}
    h_{\mathrm{sub}} = \mathrm{ramp}\Bigl(2\,\texttt{sizeof(FLT)}\, A_d(s);\ \tfrac{1}{2} C_3,\ 2\, C_3\Bigr), \qquad
    h_{\mathrm{buf}} = \mathrm{ramp}\Bigl(\beta \cdot 64\, s;\ \tfrac{1}{2} C_3,\ 2\, C_3\Bigr),
    \label{eq:traffic_ramps}
\end{equation}
where $\mathrm{ramp}(x; a, c) = \min\bigl(1, \max(0, \ln(x/a) / \ln(c/a))\bigr)$, $C_2$ is the L2 cache of one core and $C_3$ the L3 cache divided by the number of threads (Table~\ref{tab:platform}). With $\gamma = 0.94$ for the fraction of fine-grid lines that the add step has to fetch from memory, fitted to the measurements, the estimate is
\begin{align}
    \mathrm{reads}  &= (d + 1) + 2\beta\, h_{\mathrm{buf}} + (2\lambda + u)\, h_{\mathrm{sub}} + \gamma \lambda, \label{eq:spread_reads}\\
    \mathrm{writes} &= \beta\, h_{\mathrm{buf}} + (2\lambda + u)\, h_{\mathrm{sub}} + \gamma \lambda. \label{eq:spread_writes}
\end{align}
The term $d + 1$ is the coordinates and the strength of each point, read once at random; the $\beta$ terms are the staging buffer, fetched before it is written, re-read by the kernel and written back once it no longer fits; the $\lambda$ and $u$ terms are the subgrid, fetched by the zeroing, touched again by the kernel and read back by the add step once it no longer fits; and $\gamma \lambda$ is the fine grid, read and written by the add step. $S_{\max}$ moves the terms in opposite directions: raising it lowers $\lambda$ but raises $h_{\mathrm{buf}}$ and $h_{\mathrm{sub}}$, which is the trade-off described above. Against the line counts of the processor's memory controllers, the estimate of reads plus writes has a median error of $7\%$ over $360$ measured configurations of dimension, precision, density, bin size and $S_{\max}$, listed in Appendix~\ref{app:traffic}; it underestimates the writes alone by about a quarter, so it ranks configurations better than it predicts their absolute traffic.

Figure~\ref{fig:maxsp_traffic_model} compares the estimate of reads plus writes with the line counts of the memory controllers for the reference transform on $20$ threads, one per core, sweeping $S_{\max}$ with every other setting at its default. The ends of the two ramps in Equation~\eqref{eq:traffic_ramps} were fitted to this sweep together with the $54$ configurations of dimension, precision and density used elsewhere in this chapter: the subgrid and the buffer leave the cache over a narrow range around a thread's share of L3, between half and twice that share for both the subgrid and the buffer. On the $54$ configurations the median error of the estimate is $7\%$. On the reference transform it agrees with the measurements from $S_{\max} \approx 30{,}000$ upwards, to within $7\%$ except at the largest subproblem size, one per thread, where it is $11\%$ low. Below that it is too high, by $13$ to $74\%$, and the error grows as $S_{\max}$ shrinks: small subproblems are processed in sorted order, so consecutive subproblems add into neighbouring parts of the fine grid while those lines are still cached, a reuse the constant $\gamma$ does not capture. The estimate therefore reproduces the traffic of large subproblems and the step at which the staging buffer leaves the thread's share of the L3 cache, but overestimates the traffic of small subproblems.

\subsection{The current heuristic}
The current heuristic sets $S_{\max}$ to the minimum of $10^5$ and $M/n_{\text{thr}}$ in two and three dimensions, and to the minimum of $10^4$ and $M/n_{\text{thr}}$ in one. These constants are suboptimal, because a fixed number of points need not land on the balance point that minimises memory demand. Figure~\ref{fig:maxsp_traffic_model} shows how far the default sits from that point on the reference transform: at $S_{\max} = 10^5$ the spreading stage moves $8.2$ lines per nonuniform point between the processor and memory, against $6.4$ at $S_{\max} = 8000$, where the stage is fastest, taking $546$\,ms against $572$\,ms at the default.

\section{Bin dimensions}

Before spreading, FINUFFT sorts all points into bins with an incomplete histogram sort. Sorting is incomplete in the sense that points are grouped into bins but left in arbitrary order within a bin, which is enough to give the spreader most of the cache locality of a full sort at a fraction of its cost: the histogram sort runs in $O(n)$ time and $O(n_{\mathrm{bins}})$ space, against $O(n \log n)$ for a comparison sort. Figure~\ref{fig:binsort_locality} shows three levels of sorting applied to the same point set -- none at all, coarse bins and FINUFFT's default bins -- with each point coloured by its position in the array the spreader then reads.

By default, FINUFFT uses boxes of $16$ grid points along the fast $x$ axis and, in two or three dimensions, $4$ points along the slower $y$ and $z$ axes. These sizes are fixed in the library, but nothing about the algorithm requires them, and the rest of this section measures what they cost.
\subsection{Binsize effect on memory}

The bin size pulls the two stages in opposite directions. In the spreading stage a smaller bin means a smaller subgrid: the bin enters Equation~\eqref{eq:subgrid_1d} through the slack term $b$, paid once per subgrid, and Equations~\eqref{eq:subgrid_2d} and~\eqref{eq:subgrid_3d} in the same way through the bin rows, so with smaller bins each point brings fewer subgrid cells with it and the add step moves less data. The sort pays for this. The grid is cut into
\begin{equation}
    n_{\mathrm{bins}} = \prod_{i=1}^{d} \bigl(\lfloor N_i / b_i \rfloor + 1\bigr)
    \label{eq:nbins}
\end{equation}
bins, so halving every side of a bin multiplies their number by $2^d$, and the sort keeps state for every one of them. Each of its $n_t$ threads holds a private histogram of $n_{\mathrm{bins}}$ four-byte counters, $L_c = \lceil 4 n_{\mathrm{bins}} / 64 \rceil$ lines, and goes over its share of the points twice: a counting pass that increments the counter of each point's bin, and a placement pass that writes the point's index to the next free slot of that bin in the output array \texttt{ret}. The bins of consecutive points are random, so both passes touch the histogram at random. In the placement pass every bin also has an open line of \texttt{ret} being filled, eight eight-byte indices to a line. While the histogram and the open lines fit in the thread's share of the L3 cache, $C_3$, the sort streams the coordinates and writes \texttt{ret} once; once they do not, a counter line or an open \texttt{ret} line is evicted before the bin comes round again, and each such miss costs a DRAM read and a write-back. On the reference transform the default $16 \times 4$ bins cut the $6750^2$ fine grid into $712{,}000$ bins, a histogram of $2.85$\,MB per thread against $C_3 = 2.5$\,MB on $20$ threads, so the sort is already past that point.

The traffic can be estimated in the same terms as that of the spreading stage. A counter line is reused when a later point falls into one of the bins it holds; with bins drawn at random, the number of points between two uses of the same line is geometric with mean $L_c$. In the meantime the thread streams $c = d \cdot \texttt{sizeof(FLT)} / 64$ coordinate lines per point and touches $L_c(1 - e^{-n/L_c})$ distinct counter lines after $n$ points, so the line survives if fewer than $K = C_3 / 64$ lines have been touched in between. Writing $n^{*}$ for the gap at which the footprint reaches $K$, the probability that a counter access misses is
\begin{equation}
    P_c = e^{-n^{*}/L_c}, \qquad L_c\bigl(1 - e^{-n^{*}/L_c}\bigr) + c\, n^{*} = K,
    \label{eq:sort_counts_miss}
\end{equation}
for the counting pass, $P_{c1}$, and with the open \texttt{ret} lines added to the footprint, $+\, n_{\mathrm{bins}}(1 - e^{-n^{*}/n_{\mathrm{bins}}})$ on the left, for the placement pass, $P_{c2}$. The open \texttt{ret} lines are shared by all threads through the L3 cache, so whether they survive is decided by their total number against the whole cache: at most one per bin and thread, and never more than \texttt{ret} has lines,
\begin{equation}
    P_{\mathrm{ret}} = \max\Bigl(0,\ 1 - \frac{C_3 n_t / 64}{\min(n_t n_{\mathrm{bins}},\ M / 8) + n_t L_c}\Bigr).
    \label{eq:sort_ret_miss}
\end{equation}
Leaving out the compulsory traffic, which is the same for every bin size -- the coordinates read once by each pass, $2c$ lines, and one line of \texttt{ret} written for every eight points -- and adding the passes that zero the histograms and turn them into offsets, $\kappa = (2 n_t + 1) L_c / M$ lines per point, the bin-dependent traffic of the sort is
\begin{align}
    \mathrm{reads}  &= P_{c1} + P_{c2} + \tfrac{7}{8} P_{\mathrm{ret}} + \kappa, \label{eq:sort_reads}\\
    \mathrm{writes} &= P_{c1} + P_{c2} + \tfrac{7}{8} P_{\mathrm{ret}} + \kappa \label{eq:sort_writes}
\end{align}
lines per nonuniform point, where a missed \texttt{ret} line costs $7/8$ of a line because the one line per eight points that is filled completely belongs to the compulsory traffic. While the bins are few, $P_{c1}$, $P_{c2}$ and $P_{\mathrm{ret}}$ are zero and the sort moves little beyond its compulsory traffic; as the bins shrink, the histogram and then the open lines outgrow $C_3$, and every point adds up to three missed lines in each direction. A bin size therefore trades the add traffic of Equations~\eqref{eq:spread_reads} and~\eqref{eq:spread_writes}, which falls as the bins shrink, against the sort traffic of Equations~\eqref{eq:sort_reads} and~\eqref{eq:sort_writes}, which rises.

%The sort itself makes two passes over the points: the first counts how many fall into each bin, and the second writes each point's index into the slot its bin has been given. Nothing else is touched apart from an array of $n_{\mathrm{bins}}$ counters held privately by each thread, so the cost is governed by whether that array stays in cache rather than by how many points are being sorted. Table~\ref{tab:binsort_cost} shows the consequence: sorting reaches its fastest, about $4.5$ Gcycles per transform, once the counter array has fallen well inside the L1 data cache, which happens at a bin of $384\times96$, and coarser bins bring no further gain. The array first fits at $128\times32$, but sorting still pays $6.4$ Gcycles there, so the approach to the floor is gradual rather than sharp. The default $16\times4$ leaves $526{,}000$ bins and a $2.1$\,MB counter array per thread, and pays $26.5$ Gcycles for it, nearly six times the floor.

\subsection{Other binsize limits}

Two further limits restrict which bins are worth considering. The first is their shape, which should follow the order of the dimensions in memory, $b_x \ge b_y \ge b_z$. The fine grid is stored with $x$ contiguous, consecutive $y$ rows $N_x$ cells apart and consecutive $z$ planes $N_x N_y$ cells apart, and the bin index also runs fastest along $x$, so a subproblem fills its bins along $x$ first and its subgrid is a box of $x_{\mathrm{ext}} \times (b_y + w) \times (b_z + w)$ cells. For a given number of points, small $b_y$ and $b_z$ give a subgrid of few long rows, and tall or deep bins give one of many short rows. Each row is zeroed, spread into and added to the fine grid separately, and each starts and ends at an arbitrary place within a cache line, so every row brings about one partially used line with it, an overhead that is negligible for long rows and grows as the rows shorten. In the fine grid, moreover, every row of a subgrid lies in a different page, $N_x \cdot 2\,\texttt{sizeof(FLT)}$ bytes ($108$\,kB on the reference transform) from the next, so a tall subgrid makes the add step touch many pages per subproblem, more than the translation lookaside buffer holds, while a flat one touches few and its successors along the same bin row reuse them. Restricting the bins to $b_x \ge b_y \ge b_z$ also keeps them in the region where the subgrid formulas of Section~\ref{sec:subgrid_size} were checked against measurements. When bin size and $S_{\max}$ were selected jointly for $18$ test configurations, adding this restriction raised the geometric-mean speed-up over the default from $1.44$ to $1.49$; since $S_{\max}$ was re-selected at the same time, that comparison does not isolate the effect of the shape alone.

The second limit is the cache. Points keep an arbitrary order inside a bin, so while the points of one bin are spread, the kernel's writes scatter over the whole region the bin covers, padded by the kernel width on every side so that a point at the edge can deposit its full $w^d$ neighbourhood. That region,
\begin{equation}
    (b_x + w)(b_y + w)(b_z + w) \cdot 2\,\texttt{sizeof(FLT)} \ \text{bytes},
    \label{eq:padded_bin}
\end{equation}
is written repeatedly as the bin is consumed, and Table~\ref{tab:spread_l2} shows what happens once it leaves the L1 data cache. Up to $64 \times 16$, where the padded bin fills $0.8$ of L1d, spreading costs between $3.7$ and $4.05$ Gcycles regardless of the bin; at $96 \times 24$ and $128 \times 32$, past L1d but inside L2, it rises to $4.25$ and $4.5$ Gcycles as the misses are served by L2; and once the padded bin no longer fits in L2 either, from $192 \times 48$ onwards, it climbs to $5.8$, $8.2$ and finally $55.6$ Gcycles. A bin is therefore only allowed to grow while the padded region of Equation~\eqref{eq:padded_bin} stays within $0.9$ of L1d, which leaves room for the kernel values and the staging buffer the stage also keeps in L1. In three dimensions in double precision even the default $16 \times 4 \times 4$ bin exceeds this, at $43.5$\,kB with the padding of an $8$-point kernel, so there the default is kept.

\section{Selection algorithm}
\label{sec:selection_algorithm}

The estimates of this chapter combine into a procedure that chooses the bin dimensions and $S_{\max}$ for a given transform before it runs. Its inputs are the dimension $d$, the precision, the fine grid $N_1 \times \dots \times N_d$, the number of points $M$, the number of threads $n_{\mathrm{thr}}$, the kernel width $w$, and the sizes of the L1d, L2 and L3 caches. It assumes uniformly distributed points and needs no measurement of the input.
\begin{enumerate}
    \item \emph{Candidate bins.} Take powers of two, $b_x \in \{16, \dots, 2048\}$ and $b_y, b_z \in \{4, \dots, 64\}$, and keep those with $b_x \ge b_y \ge b_z$ whose padded region, Equation~\eqref{eq:padded_bin}, fits in $0.9$ of L1d. The library default, $16 \times 4 \times 4$, is the smallest bin allowed in every dimension; if no candidate fits, the default is the only one.
    \item \emph{Candidate subproblem sizes.} Take $40$ values of $S_{\max}$ spaced logarithmically up to $M / n_{\mathrm{thr}}$, so that every thread receives at least one subproblem, and keep those of at least $2500$ points, below which the subgrid of a subproblem is mostly padding.
    \item \emph{Estimate.} For every pair, add the DRAM lines per point of the bin sort, Equations~\eqref{eq:sort_reads} and~\eqref{eq:sort_writes}, and of the spreading stage, Equations~\eqref{eq:spread_reads} and~\eqref{eq:spread_writes}. The terms that depend on neither parameter, the coordinates and strengths read once by each stage, are the same for every pair and may be left out.
    \item \emph{Choose} the pair with the fewest lines.
\end{enumerate}
The search evaluates at most a few hundred closed-form expressions and takes well under a millisecond, which is negligible against the plan and the transform. Because the spreading stage is limited by memory bandwidth above about ten threads (Section~\ref{sec:memory_bound}), minimising the lines moved is a proxy for minimising time there; at lower thread counts it is a weaker one.

On $20$ threads the selected configurations need $1.44$ times less CPU time than the defaults on geometric mean, so they make each thread do less rather than merely move the same work around. The sort accounts for most of it: its CPU time falls $2.25$ times, against $1.10$ times for the spreading stage. The reduction is largest in one dimension, $2.10$ to $2.13$ times, where the default bins are smallest relative to the cache, and smallest in three, $1.04$ to $1.08$ times, where the bins stay at the default. On $10$ threads the reduction is $1.23$ times: the sort saves less, $1.52$ times, while the spreading stage saves as much as on $20$ threads, $1.07$ times. On one thread only the sort still saves, $1.18$ times, and the spreading stage needs the same CPU time with either configuration, so the total falls $1.07$ times. The gain on the clock therefore survives the change of measure, and at one thread it is entirely the sort's.

With exponentially distributed points the selection is $1.40$ times faster on geometric mean. One and two dimensions gain throughout, by $1.78$ to $1.80$ and $1.57$ to $1.72$ times: the sort gains about as much as with uniform points, and in two dimensions the spreading stage gains more than it does with uniform points, $1.57$ times against $1.24$, because the larger bins suit the clustered points. Three dimensions, however, become slower in $15$ of their $18$ transforms, by up to $22\%$, and the losses are largest at the densities where the selected $S_{\max}$ is largest, since clustered points make a few subproblems far more expensive than the rest. The loss is one of load balance, not of efficiency: Table~\ref{tab:selection_work} shows that the selected configurations still need $1.13$ to $1.16$ times less CPU time than the defaults in three dimensions, more than with uniform points, so the threads do less work in total, but the threads that finish early wait for the one holding the most expensive subproblem. The traffic estimate assumes uniform points and has no term for this imbalance.

\section{Conclusion}

The two parameters examined in this chapter act on the same three stages of a subproblem, and neither has a monotone effect on any of them.

The maximum subproblem size trades gathering against adding. Larger subproblems write back less total subgrid volume, because the padding of half a kernel width around each subgrid is paid once per subproblem, so adding falls steeply; gathering rises instead, and at large sizes there are too few subproblems to keep every thread busy, so the wall time of the phase grows even though the work done falls. Which of the two dominates is decided by the point density: at high density a full buffer of points covers only a small region of the grid and small subproblems are better, while at low density even a small buffer spreads over a large subgrid and large ones are better. Gathering, however, only slows down in some of these cases.  Gathering is thus insensitive to the subproblem size when few threads compete for memory and strongly sensitive when many do, which is why the trade-off against adding exists only at high thread counts: single-threaded, the best choice is simply the size that minimises the number of cells written.

The bin dimensions act through three different quantities, each with its own threshold. The sort itself is governed by the number of bins, because beyond its compulsory traffic it touches nothing but an array of counters held privately by each thread and one open line of the output per bin, and it moves little more than that compulsory traffic once these fit in the thread's share of the L3 cache -- which for the transform measured here happens only above the library's default, whose $2.85$\,MB histogram already exceeds the $2.5$\,MB share on $20$ threads. Spreading is governed by the region a bin covers once padded by the kernel, and is insensitive to the bin dimensions until that region no longer fits in cache, at which point its cost rises with the misses it causes. Adding is governed by the size of the subgrids the bins produce, which the relations of Section~\ref{sec:subgrid_size} predict, and its cost is close to proportional to the number of cells written, with a constant that holds to within about a tenth over the middle of the range and rises at both ends.

Taken together, the two parameters cannot be chosen independently of each other or of the input. The subproblem size fixes how many points a subgrid must cover, the bin dimensions fix how far apart those points may lie, and it is their combination that determines total throughput. Balance between stages shifts when the density, the dimension and the thread count change.

The proposed selection procedure turns this analysis into a choice made before the transform runs. It estimates the memory traffic of the bin sort and the spreading stage for each candidate pair of bin dimensions and $S_{\max}$, from the dimension, density, kernel width, thread count and cache sizes alone, and keeps the pair that moves the fewest lines. On $20$ threads it is faster than the library defaults on $51$ of $54$ transforms and $1.50$ times faster on geometric mean; most of the gain comes from the sort, which the larger bins make $2.2$ times faster, while the choice of $S_{\max}$ is what reduces the CPU time of the spreading stage. Its limits follow from what the traffic estimate leaves out. With fewer threads spreading is no longer bound by bandwidth and the gains shrink, to $1.23$ times on $10$ threads and $1.07$ on one. The estimate has no term for load imbalance, which causes the three slowdowns on $20$ threads, and it assumes uniformly distributed points: with exponentially distributed points one and two dimensions still gain, but three dimensions become slower in $15$ of $18$ transforms.
