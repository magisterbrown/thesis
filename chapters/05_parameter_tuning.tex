\chapter{Model Evaluation}
\label{ch:parameter_tuning}

This chapter tests the models of Chapter~\ref{ch:sigma_selection} against measurement, to establish how far each can be trusted when it is used to choose a configuration. A model is useful for selection if it ranks configurations in the same order as their measured cost, even where its absolute values are off, so each comparison asks both whether the predicted values agree with measurement and whether the predicted optimum lies where the measured one does.

The chapter follows the order of the models. It first validates the two costs of the upsampling factor. It then confirms that spreading is limited by memory bandwidth on a machine whose cores are all in use, the assumption on which the models of the spreader parameters rest, and compares the predicted subgrid size, memory traffic and cache limit of the bins with measurement. Finally, it evaluates the selection algorithm built on these models against the library defaults on a set of test transforms that differ from the reference transform the models were developed on.

\section{Upsampling factor}

The cost model of the upsampling factor consists of two parts that move in opposite directions, the spreading work and the FFT, and they are validated separately. Both were measured with Google Benchmark~\cite{googlebenchmark} on the platform of Section~\ref{sec:platform}: spreading on a single thread, where its cost follows the operation count the model predicts, and the FFT on one thread and on all threads, to show where its cost departs from the asymptotic estimate.

\subsection{Validating the Spreading Cost Model}
\label{sec:validate_spreading}

To validate the $w^d$ scaling predicted by the model, spreading time was measured on a single thread across one, two and three dimensions for a range of $\sigma$ values at tolerance $\varepsilon = 10^{-6}$. As shown in Figure~\ref{fig:sigma_sweep_1e6}, the theoretical curves follow the same trajectory as the measurements, including the location of the minimum. The one exception is the step the model predicts at $\sigma = 1.35$ in two dimensions, which the measurement does not show. Throughput changes in steps, because spreading is vectorised and at every kernel size the number of operations rounds up to the nearest multiple of the SIMD width. Figure~\ref{fig:sigma_sweep_all} in Appendix~\ref{app:maxsp_sweeps} shows the same graphs for a range of common transform configurations at several tolerances.

\subsection{Validating the FFT Cost Model}
\label{sec:validate_fft}

Figure~\ref{fig:ducc_fft_scaling} tests the $\mathcal{O}(\tilde{N} \log \tilde{N})$ asymptotic guide
against measured DUCC FFT throughput. If the cost per butterfly were constant, the achieved
throughput would decay as $1/\log_2 \tilde{N}$, drawn as the dash-dotted reference in
each panel. The measurements depart from the model in two regimes.
First, for small transforms the throughput increases with grid size, because the fixed
per-call overhead is amortised over an increasing number of points. For larger transforms
the single-threaded throughput follows the $1/\log_2 \tilde{N}$ trend. The throughput of a
transform that uses all threads on the machine, however, keeps increasing as long as the
grid it works on fits in the L3 cache: the array is complex, at $16$ bytes per cell in
double precision, so the condition is $16\,\tilde{N} \le$ L3, which on the platform of
Section~\ref{sec:platform} is $16\,\tilde{N} \le 50$\,MiB, that is $\tilde{N} \le 3.3$
million cells. The vertical line in each panel marks where that bound is crossed.
DUCC implements the FFT with the mixed-radix Cooley--Tukey algorithm inherited from FFTPACK
(Section~\ref{sec:related_ducc}). Each of its $\mathcal{O}(\log \tilde{N})$ passes performs only a
few arithmetic operations per element, whether the transform runs on one thread or many, so it is
limited by memory bandwidth rather than by arithmetic throughput. As long as all points fit in the L3
cache, the successive passes over the array are served without loads from main memory. Once
the array spills into main memory, the parallel version also settles onto the
$1/\log_2 \tilde{N}$ trend.

\section{Spreading Is Memory Bound}
\label{sec:memory_bound}

To find out what limits the spreading stage, the reference transform (Section~\ref{sec:workload}) was run with the library defaults at $1$ to $20$ threads and at all $40$ hardware threads, and two quantities were recorded over the spreading loop alone. The first is the traffic between the processor and main memory, read from the memory controllers' own counters of 64-byte line reads and writes; divided by the wall time of the loop it gives the DRAM bandwidth the stage consumes. The second is the number of instructions the threads retire per cycle (IPC), read from each thread's core counters around the gather, spread and add steps. Multiplied by the thread count, IPC becomes the instruction throughput of the whole processor. Each point is the median of three runs. Figure~\ref{fig:memory_bound} shows both quantities.

\begin{figure}[ht]
    \centering
    \includegraphics[width=0.85\textwidth]{figures/memory_bound/scaling.pdf}
    \caption{DRAM bandwidth (top) and summed IPC (bottom) of the spreading stage against thread count, reference transform. Dotted: one thread scaled linearly; shaded: two hardware threads per core.}
    \label{fig:memory_bound}
\end{figure}

Figure~\ref{fig:memory_bound} shows that spreading scales almost linearly up to four threads. Beyond that it falls below linear scaling, and above ten threads its DRAM bandwidth saturates at about $30$\,GB/s, as the roofline model~\cite{williams2009roofline} predicts for a bandwidth-bound kernel. Between ten and twelve threads spreading becomes slower still. At that point the subgrid addition switches from a critical section to a lock-free algorithm~\cite[Sec.~3.7, p.~60]{herlihyshavit2012}, which guarantees system-wide progress regardless of how the threads are scheduled, but executes more instructions for every grid cell it updates.

Above about twelve threads, therefore, the spreading stage is memory bound: its time is set by how much data it moves between the processor and main memory, not by how many instructions it executes. The amount moved is not a fixed property of the transform. It grew from $4.0$ to $8.2$ lines per nonuniform point between one and twenty threads, because the share of the L3 cache available to each thread shrinks as threads are added. It also depends on how the configuration lays out the work. The subproblem size $S_{\max}$ fixes how large each subgrid and gather buffer is, and so whether they stay in cache. The bin dimensions fix the order of the points, and $\sigma$ fixes the size of the fine grid and the width of the kernel. Improving spreading on a machine whose cores are all in use therefore requires understanding how each of these parameters affects the memory demand of the stage.

\section{Evaluation Workloads}
\label{sec:eval_workloads}

The selection procedure of Section~\ref{sec:selection_algorithm} was evaluated on a wider set of $54$ test transforms rather than on the reference transform alone, so that it was tested on inputs it had not been designed around. The set covered one, two and three dimensions, single and double precision, and nine point densities from $0.125$ to $32$ points per fine-grid cell, in all combinations. Every test transform had at least $4.2$ million points, a kernel of $8$ points and an upsampling factor of $2$, so that only the bin dimensions and $S_{\max}$ differed between the default and the selected configurations. The points were distributed uniformly, which is the distribution the traffic model assumes, and, on $20$ threads, also exponentially, which clusters them towards one corner of the grid and so tests the procedure outside that assumption. Each transform was run on $1$, $10$ and $20$ threads with both the default and the selected configuration. The comparison used the time of the bin sort plus the spreading stage, the two stages the selected parameters act on, and summarised the ratio of default to selected time as a geometric mean over the transforms of each group.

The gains are largest in one dimension, $1.99$ to $2.10$ times, and smallest in three dimensions, only $1.07$ to $1.13$ times, where no bin larger than the default fits in L1d, so the procedure keeps the default $16 \times 4 \times 4$. Of the eight transforms that became slower on $20$ threads, six are of this kind, by at most $6\%$: the selected $S_{\max}$ is large enough to leave each thread only a few subproblems, so the work is unevenly divided among the threads, an effect the traffic estimate does not contain. The other two are sparse two-dimensional transforms in double precision, $1\%$ and $12\%$ slower, for which the estimate favours a configuration that the measurement does not.

With fewer threads the gains shrink. Spreading is then limited by latency and computation rather than by bandwidth, so savings in DRAM traffic no longer show in the run time, and in three dimensions, where the bins do not change at all, the selection is no better than the defaults.
