\chapter{Introduction}
\label{ch:introduction}

\section{Motivation}

The nonuniform fast Fourier transform is a workhorse of computational science. It underlies image reconstruction in magnetic resonance imaging, gridding in radio interferometry, particle-mesh methods in molecular dynamics and cosmology, and cryo-electron microscopy, and in each of these it is often the dominant cost of the pipeline that contains it. FINUFFT is among the most widely used implementations, and a large body of work has gone into making its inner loops fast: a carefully chosen kernel, hand-vectorised evaluation, and a parallel spreading scheme that avoids contention between threads.

What has received far less attention is how the library should be \emph{configured}. FINUFFT's behaviour is governed by a set of parameters -- the upsampling factor that fixes the size of the intermediate grid, the maximum size of a spreading subproblem, the dimensions of the boxes the nonuniform points are sorted into, and several others -- and their values are chosen by heuristics fixed when the library is built or, at best, by simple rules evaluated at run time. Several are not exposed to the user at all. These heuristics are not arbitrary; they encode real experience. But they are fixed, while the transforms the library is asked to perform are not.

The consequences of a poor choice are not small. A configuration search over a single representative transform, reported in Chapter~\ref{ch:parameter_importance}, produces execution times spanning more than an order of magnitude, and the parameters responsible for that spread are precisely the ones a user is least equipped to reason about. A library that is otherwise carefully optimised can therefore be run, without any indication that anything is wrong, in a configuration several times slower than one a few keystrokes away.

\section{Problem Definition}

FINUFFT exposes a number of configuration parameters through which a user can tune the performance of a particular transform. Tuning them is difficult in practice, because the parameters that matter most have no obvious interpretation: each acts not on the transform as a whole but on its individual steps, and on different steps in opposite directions.  

Lacking any basis on which to prefer one value to another, a user tunes by trying values, measuring, and keeping whichever happened to be fastest. That is slow, it gives no reason to expect the winning value to remain the right one for a different input or a different machine, and it offers no way to distinguish a real effect from measurement noise. Nor can the difficulty be resolved simply by measuring more carefully: a parameter that halves one step and doubles another leaves the total unchanged, so an end-to-end timing reveals neither which step moved nor why.

\section{Approach}

Because the parameters act on individual steps and in opposing directions, a transform is separated into the steps they act on -- sorting, spreading and the FFT -- and each parameter's effect is measured on each step in turn. Spreading is itself divided further. It processes the sorted points in independent chunks, called subproblems, which are distributed across threads, and each subproblem passes through three internal stages: gathering its points out of the sorted arrays, evaluating the kernel around each of them into a private subgrid, and adding that subgrid back into the shared fine grid.
These three stages run inside a single parallel region, so they cannot be timed separately with a clock. They are separated instead with a sampling profiler, which attributes the processor's cycles to the function executing at the time, and hardware performance counters recorded alongside identify the mechanism behind each effect: the level of the cache hierarchy a working set no longer fits in, contention between threads for memory, or the balance of work across them.

Wherever possible, the quantities that govern these trade-offs are captured in closed-form models, derived from the structure of the algorithm and the specification of the processor and validated against the library's own behaviour. Each analysis is carried out across dimensions, point densities, tolerances and thread counts, since a parameter that is irrelevant in on one stage can be decisive in another. Chapter~\ref{ch:methodology} describes the test platform, the workloads and the measurement methodology in detail.

\section{Research Questions}

This thesis addresses the following questions.

\begin{enumerate}
    \item \textbf{Which configuration parameters affect performance, and how much?} FINUFFT exposes a dozen options and hides several more constants in its source. Chapter~\ref{ch:parameter_importance} establishes where the time is spent across the stages of a transform, and ranks the parameters by their contribution to the variance in execution time over a joint search of the configuration space.

    \item \textbf{Through which mechanism does each parameter act, and where do the resulting trade-offs balance?} Rather than treating the transform as a single measurement, Chapters~\ref{ch:sigma_selection} and~\ref{ch:parameter_tuning} separate it into sorting, gathering, spreading, adding and the FFT, and attribute the effect of each parameter to the steps it speeds up and the steps it slows down. Because those effects oppose one another, each parameter has an interior optimum, and the question is what its position depends on: point density, dimension, requested tolerance, thread count, and the sizes of the levels of the cache hierarchy.

\end{enumerate}

\section{Contributions}

The main contributions of this thesis are the following.

\begin{itemize}
    \item \textbf{A per-stage measurement of the spreading phase.} The three stages a subproblem passes through -- gathering, kernel evaluation and adding -- run inside a single parallel region and cannot be timed with a clock. They are separated here by attributing sampled processor cycles to the functions that implement them, with hardware performance counters recorded alongside, so that the effect of every parameter can be traced to the stage it acts on and to the cause: cache capacity, memory contention between threads, or load imbalance.

    \item \textbf{A ranking of FINUFFT's configuration parameters.} A Gaussian-process search over six parameters of a one-gibibyte two-dimensional transform, including two that the library does not expose, attributes the variance in execution time to each of them (Chapter~\ref{ch:parameter_importance}). Sorting dominates, and once it is enabled the upsampling factor and the sort bin dimensions account for most of what remains, while the maximum subproblem size is insensitive over the whole range in which it can act. The best configuration found is $5.2\%$ faster than the library defaults.

    \item \textbf{Cost models for the upsampling factor.} Chapter~\ref{ch:sigma_selection} models the two costs that $\sigma$ trades against each other. The spreading model reproduces the measured cost across one, two and three dimensions and can locate the $\sigma$ that minimises spreading without profiling; the FFT model ranks candidate values correctly at a fixed problem size but does not predict absolute cost, because its constant is set by the memory hierarchy. The optimum generally lies inside $[1.25, 2.00]$, where the library's two-valued heuristic cannot reach it.

    \item \textbf{Closed-form models of subgrid size.} Chapter~\ref{ch:parameter_tuning} derives the average size of the subgrid produced by a given subproblem size and bin shape in one, two and three dimensions, and validates it to within one percent against subgrids logged by the spreader. Since the cost of the adding stage is proportional to the number of cells written, the model predicts that cost for configurations that were never measured.

    \item \textbf{An account of the subproblem size and bin size trade-offs.} The same chapter shows that point density decides whether gathering or adding sets the best subproblem size, and that the sort bin dimensions act on three stages through three different quantities: the sort through the size of its counter array against the first-level cache, spreading through the padded area of a bin against the first and second levels, and adding through the subgrid area. To measure them, the bin dimensions were exposed as options of the library.
\end{itemize}
