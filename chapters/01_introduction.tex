\chapter{Introduction}
\label{ch:introduction}

This thesis studies how the configuration parameters of FINUFFT, a widely used
library for the nonuniform fast Fourier transform, affect the time a transform
takes, and whether that effect can be modelled well enough to choose better
values than the library's defaults. This chapter explains why the question
matters, states the problem and the scope of the study, and sets out its
research questions and contributions.

\section{Background and Motivation}

In many scientific applications, including frequency analysis, data are sampled
at irregular locations rather than on a uniform grid. A magnetic resonance
scanner samples along spirals or radial spokes, a radio interferometer samples
wherever its pairs of antennas happen to point, and a molecular dynamics code
analyses particles that move continuously through space. Analysing such data in
the frequency domain calls for a Fourier transform between scattered points and
uniform frequencies. Evaluating that transform directly costs $O(MN)$ operations
for $M$ points and $N$ frequencies, and the fast Fourier transform, which would
reduce the cost to $O(N \log N)$, applies only to samples that are equally
spaced. The nonuniform fast Fourier transform bridges the two. It spreads each
scattered point onto a fine uniform grid using a smooth kernel of finite width,
transforms that grid with an ordinary FFT, and then divides out the effect of
the kernel, recovering the speed of the FFT at an accuracy the caller requests
in advance.

The cost of that construction matters because it is rarely paid once. Iterative
image reconstruction in magnetic resonance imaging evaluates a transform and its
adjoint at every iteration; gridding in radio interferometry repeats one for
every frequency channel and every time step; particle-mesh methods in molecular
dynamics and cosmology evaluate one at every step of the simulation. In each of
these pipelines the transform is frequently the single most expensive component,
so the rate at which it runs sets the rate at which the surrounding computation
runs.

FINUFFT~\cite{barnett2019} is among the most widely used implementations.
Considerable effort has gone into making its inner loops fast: a spreading
kernel, which distributes each point's value over the nearby cells of the fine
grid, shaped so that it can be evaluated cheaply at run time; hand-vectorised
evaluation of that kernel; and a parallel spreading scheme in which each thread accumulates
into a private subgrid, so that threads do not contend for the shared output
grid. Beyond these loops, its performance depends on a set of configuration
parameters whose values the library fixes by default: the upsampling factor, the
maximum subproblem size, the bin dimensions, whether the points are sorted, and the
thread count above which the adding stage switches to atomic updates. This
thesis concentrates on the first three, whose best values depend on the
transform. The upsampling factor sets how much larger the fine grid used for
spreading is than the output grid; the maximum subproblem size sets how many points a
thread spreads at a time; and the bin dimensions set the size of the boxes the
points are sorted into before spreading.

Two properties make FINUFFT a suitable subject for studying how these parameters
affect performance. It is in production use, so its behaviour affects real
workloads rather than a benchmark written for the occasion. And it is built like
the other implementations of the algorithm, sorting the points into bins and
spreading them in independent subproblems, so what is learned about where its
time goes is not peculiar to it.

How long a transform takes is therefore not settled by the quality of those
inner loops alone. The algorithm proceeds in stages -- sorting the nonuniform
points, spreading them onto the fine grid, transforming that grid, and
correcting for the kernel afterwards -- and the configuration parameters decide
how much work each stage is given. A parameter that shrinks the work in one stage usually
enlarges it in another, so the fastest configuration is a balance rather than an
extreme. Unless the user overrides them, FINUFFT chooses these values itself,
some by simple heuristics and others from constants fixed when the library is
built. How well it chooses, and what is lost when it chooses badly, is the
subject of this thesis.

\section{Problem Statement}
\label{sec:problem_statement}

FINUFFT chooses the values of its configuration parameters automatically, but
mostly from fixed constants or simple rules rather than from the transform at
hand. The user may override all of them except the bin dimensions:
\begin{itemize}
    \item the \emph{upsampling factor} $\sigma$ is $1.25$, or $2$ when the point
    density or the requested accuracy is high;
    \item the \emph{maximum subproblem size} $S_{\max}$ is $10^5$ points in two
    and three dimensions and $10^4$ in one, or fewer if a thread has fewer points
    than that;
    \item the \emph{bin dimensions} are $16$ grid cells along the $x$ axis and
    $4$ along the others, a constant compiled into the library;
    \item \emph{sorting} is decided by a heuristic, and is enabled for inputs of
    realistic size;
    \item the \emph{atomic-update threshold} is $10$ threads.
\end{itemize}
These defaults were tuned by the authors for common combinations of transform
and CPU, but they stay the same while transforms vary widely in dimension,
point density, accuracy, thread count and the machine they run on.

The right value is hard to guess because each parameter affects performance
nonlinearly, through more than one stage of the transform. A type-1 transform
runs in four stages: the points are \emph{sorted} into bins; they are
\emph{spread} onto a fine grid, with each thread gathering a subproblem of
points, spreading them into a private subgrid and adding that subgrid to the
shared grid; the grid is transformed by an \emph{FFT}; and the result is
\emph{deconvolved} to remove the effect of the kernel.

Consider the upsampling factor, which fixes how much larger the fine grid is than
the output grid. Raising it enlarges that grid, so the
FFT in the middle of the algorithm transforms more data and takes longer. But a
finer grid also places the aliases the spreading kernel produces further apart,
so a narrower kernel suffices for the same accuracy, and spreading touches fewer
cells for every point it deposits. One stage is made more expensive and another
cheaper by the same change, and which effect wins depends on how many points
there are per grid cell, on how much accuracy was asked for, and on how much of
the grid fits in cache. The maximum size of a spreading subproblem and the
bin dimensions behave the same way: the subproblem size trades gathering
against adding, and the bin dimensions trade the cost of the sort against
that of spreading and adding. A user who wants to set them well therefore needs to
know not that the parameter is important, but which stages it moves, in which
directions, and what decides where the two effects balance.

A faster configuration often exists. Beatty et al.~\cite{beatty2005}
showed that the conventional upsampling factor of two is not required: a whole
family of upsampling factors and kernel widths reaches any given accuracy, so
the grid can be made smaller if the kernel is made wider. How to choose within
that family has been approached by measurement. gNUFFTW~\cite{ou2017} tunes a
GPU nonuniform transform by running candidate configurations during planning and
keeping the fastest, and reports order-of-magnitude gains from the oversampling
ratio alone. FFTW~\cite{frigo2005} does the same for the ordinary FFT, assembling
each transform from interchangeable steps and timing the candidates on the
machine it finds itself on. General frameworks such as OpenTuner~\cite{ansel2014opentuner}
apply the idea to arbitrary programs. What all of these produce is a
configuration that is fast for a specific input, on the machine where the search
was run.

They do not produce an explanation, and three things follow from that. A search
executes many transforms before it returns anything, so it repays itself only when
the same plan is executed many times, which is not how a library call is
typically used. Its answer carries no reason, so nothing about it transfers: a
value found at one point density, or on one cache hierarchy, says nothing about
another, and the search must be repeated. Moreover, a search cannot say which part of
the transform it improved, because it sees only the total. That last limitation
is not an accident of how searches are built. A parameter that halves the cost
of one stage and doubles the cost of another leaves the total unchanged, so an
end-to-end timing reports no effect where two large effects have cancelled.
Measuring the stages separately is not straightforward either: gathering,
spreading and adding all run inside a single OpenMP parallel region -- one
block of code that every thread executes at once, each on its own subproblem --
so no timer placed outside the library can separate them.

The missing knowledge is therefore not which configuration is fastest, which a
search can already find, but how the cost of each stage depends on each
parameter, and what fixes the point at which the opposing effects balance. With
that, the cases in which the library's defaults are adequate could be
distinguished from those in which they are not.

\section{Thesis Objective and Scope}

The objective of this thesis is to explain how FINUFFT's configuration
parameters determine the time a transform takes, to model those effects in terms
of quantities known before the transform runs, and to use the models to choose
better values than the defaults. Section~\ref{sec:research_questions} breaks
this objective into three research questions.

The study is limited in four ways. It examines \emph{type-1 transforms}, in
which scattered points are spread onto a uniform grid; type-2 transforms are not
measured, and a type-3 transform appears only in the stage breakdown of
Chapter~\ref{ch:parameter_importance}. All three dimensions are covered, with
the two-dimensional case as the reference workload, mostly in double precision;
single precision is measured where it matters, in
Chapters~\ref{ch:sigma_selection} and~\ref{ch:parameter_tuning}. All
measurements were taken on a \emph{single machine}, the Intel Xeon E5-2698 v4
described in Section~\ref{sec:platform}, referred to as the machine under test.
Finally, \emph{accuracy is held fixed}: FINUFFT derives the kernel width from the
requested tolerance, so every configuration compared meets the same error
target.

The parameters studied are those listed in
Section~\ref{sec:problem_statement}, with the bin dimensions counting as two
parameters, $b_x$ and $b_y$, in the two-dimensional reference workload, six in
total. The bin dimensions had to be exposed as run-time options first, since
the released library fixes them at compile time. The remaining options are
excluded because they do not affect the transforms studied here;
Section~\ref{sec:finufft_parameters} lists them and gives the reason in each
case. The upsampling factor, the maximum subproblem size and the bin dimensions
are modelled, and for the latter two the thesis also proposes and evaluates a
selection procedure.

\section{Thesis Organization}

The remainder of this thesis is organised as follows.
Chapter~\ref{ch:background} introduces the nonuniform fast Fourier transform,
the structure FINUFFT gives it, and the prior work on choosing parameters by
measurement.
Chapter~\ref{ch:methodology} describes the machine, the workloads and the
instrumentation on which every later measurement rests, including how the
stages of a subproblem are separated from one another.
Chapter~\ref{ch:parameter_importance} establishes where a transform spends its
time and which of the six parameters account for the variation in it, narrowing
the field for the two chapters that follow.
Chapter~\ref{ch:sigma_selection} takes the upsampling factor, the highest-ranked
of them, and analyses and models the two costs it trades against each other.
Chapter~\ref{ch:parameter_tuning} does the same for the parameters that govern
the spreader -- the maximum subproblem size and the bin dimensions -- and derives the model of subgrid size on which
their behaviour rests; it then combines these results into a model of memory
traffic, proposes a procedure that selects the bin dimensions and the maximum
subproblem size from it, and evaluates that procedure on $54$ transforms.
Chapter~\ref{ch:conclusion} answers the research questions, states the
limitations of the study, and outlines future work.

\section{Research Questions}
\label{sec:research_questions}

This thesis addresses three questions.

\begin{enumerate}
    \item \textbf{Which of FINUFFT's configuration parameters affect performance
    significantly on the machine under test?} An answer names the parameters whose
    values change the execution time of a transform appreciably, and identifies
    for each the stages whose cost it reduces and the stages whose cost it raises.

    \item \textbf{Can models describe how changing each parameter affects the
    cost of the individual stages of the transform?} An answer gives, for each
    stage a parameter acts on, a model of its cost in terms of the input and of
    machine properties such as cache sizes rather than measured times, and states
    how far the model reaches: whether it predicts an absolute cost, only the
    ordering of candidate values, or only the point at which a trend changes.

    \item \textbf{Can such models choose a better configuration before a
    transform runs?} An answer uses the models to show where the defaults lie
    relative to the balance point of each trade-off, proposes a selection
    procedure built only on quantities known in advance, measures it against the
    defaults over a range of transforms, and identifies where and why it fails.
\end{enumerate}

\section{Contributions}

The contributions of this thesis are of four kinds: a way of measuring where a
transform spends its time, a set of measurements made with it, models that
predict measurement results, and a selection procedure built
on those models.

\paragraph{Methodological}
\begin{itemize}
    \item \textbf{A way to measure the cost of the steps inside a parallel
    region.} Steps that run interleaved on all threads inside one OpenMP
    parallel region cannot be separated by a timer.
    Instead, the profiler \texttt{perf} records which function the processor is
    executing at regular intervals, and the share of samples in each function
    gives that step's share of the time. Hardware counters recorded in the same
    way, such as cache misses, then show why a step became slower: because its
    data no longer fit in cache, because threads competed for memory, or
    because some threads had more work than others.

    \item \textbf{An instrumented build in which the bin dimensions are
    settable.} Bin dimensiosn are compile-time constants in the released library, and
    exposing them as options is what makes it possible to study bin size effects on performance.
\end{itemize}

\paragraph{Empirical}
\begin{itemize}
    \item \textbf{Explores better than default parameter configurations.} A
    search that varies all six parameters together finds configurations faster
    than the library defaults, the best of them by $23.3\%$ on the reference
    transform. The same search shows which parameters matter: whether the points
    are sorted dominates, and once sorting is enabled, the upsampling factor and
    the bin dimensions account for most of the remaining variation.

    \item \textbf{An explanation of the spreader parameters' trade-offs.} Each
    parameter makes one stage cheaper and another more expensive, and the
    balance shifts when the data a stage uses no longer fits in a cache level.
    Larger subproblems make adding cheaper but gathering more expensive; larger
    bins make sorting cheaper but spreading and adding more expensive.
\end{itemize}

\paragraph{Modelling}
\begin{itemize}
    \item \textbf{A closed-form model of subgrid size.} The average size of the
    subgrid produced by a given subproblem size and bin shape is derived in one,
    two and three dimensions and validated against
    subgrids logged by the spreader. 

    \item \textbf{Cost models for the upsampling factor.} The cost of spreading
    as a function of the upsampling factor is reproduced across all three
    dimensions, so the effect of raising the upsampling factor on that stage can be evaluated without profiling.
    The cost of the FFT behaves differently depending on whether the fine grid
    fits in the last-level cache, at a grid size set by the cache rather than
    fitted to measurements.

    \item \textbf{A memory traffic model of the bin sort and the spreading
    stage.} The DRAM lines moved per point by each stage are expressed in terms
    of the bin dimensions, the maximum subproblem size, the kernel width, the
    density, the thread count and the cache sizes.
\end{itemize}

\paragraph{Proposed model.}
\begin{itemize}
    \item \textbf{A selection procedure for the bin dimensions and the maximum
    subproblem size.} It evaluates the traffic model over combinations of maximum subproblem size and bin dimensions
    and picks one that generates least memory traffic. 
\end{itemize}
