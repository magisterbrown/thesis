\chapter{Exploring Parameter Importance}
\label{ch:parameter_importance}

\section{Overview}

Before attempting to optimize FINUFFT's parameters, it is necessary to understand which parameters actually matter and to what degree. This chapter presents a systematic sensitivity analysis of FINUFFT's configuration space. We vary each parameter independently while holding others fixed, and measure the resulting effect on execution time across a representative range of inputs. We first identify where transform time is actually spent across the three transform types (Section~\ref{sec:stage_breakdown}), then use a global, Gaussian process based search to rank the tunable parameters by their contribution to performance (Section~\ref{sec:gp_sensitivity}). The resulting ranking motivates the choice of parameters treated in depth in Chapters~\ref{ch:sigma_selection} and~\ref{ch:parameter_tuning}.

\section{FINUFFT's Configuration Parameters}

FINUFFT exposes its tunable behaviour through a single options structure called \texttt{finufft\_opts}. Its fields fall into three groups. Data handling options (\texttt{modeord}, \texttt{spreadinterponly}) change the convention used to order output modes or restrict the call to spreading/interpolation only, and do not by themselves change the amount of work performed. Diagnostic options (\texttt{debug}, \texttt{spread\_debug}, \texttt{showwarn}) control logging and are irrelevant to performance. The remaining, performance relevant options are:
\begin{itemize}
    \item \texttt{nthreads}: number of threads used for the transform.
    \item \texttt{fftw}: planner flags passed to FFTW, trading planning time for potentially faster plans.
    \item \texttt{spread\_sort}: whether nonuniform points are sorted before spreading (\texttt{0} off, \texttt{1} on, \texttt{2} heuristic choice).
    \item \texttt{upsampfac}: the upsampling factor $\sigma$, treated in depth in Chapter~\ref{ch:sigma_selection}.
    \item \texttt{spread\_thread} and \texttt{maxbatchsize}: control how work is split across threads when multiple strength vectors share the same nonuniform points (vectorized calls, $n_{\mathrm{tr}} > 1$).
    \item \texttt{spread\_nthr\_atomic}: thread count above which the spreader switches from an OpenMP critical section to atomic updates.
    \item \texttt{spread\_max\_sp\_size}: the maximum subproblem size used by the spreader, treated in depth in Chapter~\ref{ch:parameter_tuning}.
\end{itemize}
Two further fields, \texttt{spread\_kerevalmeth} and \texttt{spread\_kerpad}, are retained only for binary compatibility and have no effect on current versions of the library. A third, \texttt{spread\_kerformula}, is reserved for internal debugging. All three are therefore excluded from the analysis that follows.

\section{Where Does Time Go? Stage-Level Breakdown}
\label{sec:stage_breakdown}

Every FINUFFT call proceeds through three stages, introduced in Chapter~\ref{ch:background}: \texttt{makeplan}, which precomputes kernel coefficients and creates the FFTW plan; \texttt{setpts}, which sorts and preprocesses the nonuniform points; and \texttt{execute}, which performs the actual spreading, FFT, and deconvolution. Before deciding which configuration parameters deserve attention, it is useful to know how much of the total runtime each stage typically accounts for, since a parameter that only affects a negligible stage cannot meaningfully improve overall performance.

Using the benchmark configurations distributed with FINUFFT (covering a range of precisions, tolerances, dimensions, and both extremal values of $\sigma$), each call was timed and the three stage durations were normalised so that they summed to one. Figure~\ref{fig:stage_breakdown} shows the resulting distribution, split by transform type. For type 1 and type 2 transforms, \texttt{execute} dominates, accounting for the large majority of the total time, while \texttt{setpts} contributes a smaller but non-negligible share and \texttt{makeplan} is close to zero in almost every case. Type 3 transforms show a markedly different balance: \texttt{setpts} and \texttt{execute} contribute comparable shares, reflecting the additional preprocessing type 3 transforms require to handle nonuniform points on both sides of the transform.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.85\textwidth]{figures/parameter_importance/stage_breakdown.pdf}
    \caption{Fraction of total call time spent in each stage (\texttt{makeplan}, \texttt{setpts}, \texttt{execute}), by transform type.}
    \label{fig:stage_breakdown}
\end{figure}

This picture was refined further by instrumenting \texttt{setpts} itself, splitting it into its constituent substeps: precomputing kernel Horner coefficients, evaluating the kernel Fourier series used for deconvolution, and creating the FFTW plan. These substeps behave largely as fixed, per-call overheads rather than costs that scale with the number of nonuniform points $M$, which is consistent with \texttt{makeplan} and the fixed portion of \texttt{setpts} contributing a shrinking fraction of total time as $M$ grows.

Together, these observations indicate that parameters affecting the \texttt{execute} stage, and specifically the spreading and FFT steps within it, offer the largest potential impact on performance, with parameters affecting \texttt{setpts} becoming relevant mainly for type 3 transforms or when $M$ is small enough that fixed overheads are not amortised.

\section{Global Sensitivity Analysis via Gaussian-Process Optimization}
\label{sec:gp_sensitivity}

Stage-level timing shows which stage costs time, but not which of the many configuration parameters within that stage is responsible, nor how the parameters interact. To rank the parameters directly, a Gaussian process based optimizer (as implemented in Optuna~\cite{optuna2019}) was used to search the joint space of \texttt{modeord}, \texttt{spread\_sort}, \texttt{upsampfac}, \texttt{spread\_nthr\_atomic}, and \texttt{spread\_max\_sp\_size}, minimising the measured execution time of a single representative type 1 transform (two dimensions, $320\times320$ modes, double precision, $M=10^7$ nonuniform points, $\mathrm{tol}=10^{-9}$). \texttt{nthreads} was fixed at 8 for every trial. \texttt{spread\_thread} and \texttt{maxbatchsize} were left out of the search, since both only affect vectorized calls ($n_{\mathrm{tr}} > 1$) and the representative workload here uses a single strength vector; the FFTW planner flag and the internal kernel formula selector were likewise excluded, as neither is intended to be tuned per call.

With the best configuration found by the optimizer, the transform completed in 96\,ms, compared to 119\,ms under FINUFFT's default configuration (\texttt{spread\_sort=2} heuristic, \texttt{upsampfac} auto-selected, and all other options at their library defaults), a 19\% reduction in execution time. Table~\ref{tab:gp_best} lists the parameter values that achieved this result. Figure~\ref{fig:gp_histogram} shows the distribution of execution times across all completed trials on a logarithmic axis, with the default configuration's time marked for reference. The majority of trials cluster within a factor of a few of the default, but a heavy right tail of badly performing configurations extends more than three orders of magnitude beyond it, up to 400\,s for the single worst trial; the best configuration found sits at the front edge of this main cluster rather than being an isolated outlier itself, indicating that a good configuration is common, but a small, specific region of the search space is catastrophically bad.

To quantify the relative contribution of each parameter, functional ANOVA importance scores were computed from the completed trials. Figure~\ref{fig:importance} shows the result. \texttt{spread\_max\_sp\_size} accounts for the large majority of the variance in execution time (92\%), followed by \texttt{spread\_sort} (5\%); together they explain over 97\% of the measured variance across trials. \texttt{upsampfac} and \texttt{modeord} each contribute only a few percent or less, and \texttt{spread\_nthr\_atomic} is negligible.

    \label{fig:importance}
\end{figure}

The dominance of \texttt{spread\_max\_sp\_size} is explained by the mechanism explored in depth in Chapter~\ref{ch:parameter_tuning}: an ill-chosen subproblem size forces the spreader into either excessive scheduling overhead, when subproblems are far too small, or poor load balancing across threads, when they are too large, and both failure modes can cost orders of magnitude relative to a well-chosen size, as seen in the multi-second-to-400-second outliers of Figure~\ref{fig:gp_histogram}. \texttt{spread\_sort} contributes a smaller, but still clearly non-negligible, share: sorting nonuniform points by spatial location keeps each thread's working set localised, which directly affects cache behaviour. For this particular input, the best value found, \texttt{spread\_sort=1} (on), matches the outcome FINUFFT's own default heuristic already selects, so its share of the importance score reflects the cost of getting it wrong rather than headroom left on the table by the default. \texttt{upsampfac}, by contrast, ranks low here despite Chapter~\ref{ch:sigma_selection} showing that, for other input configurations, its choice can change execution time by tens of percent. This is not a contradiction: the importance scores in this section describe a single representative workload, and both \texttt{spread\_max\_sp\_size} and \texttt{spread\_sort} admit far more extreme perturbations, within this search, than any value of $\sigma$ the optimizer sampled. Where $\sigma$'s effect is large is precisely where FINUFFT's existing two-valued heuristic is coarsest, which is what motivates a dedicated, input-dependent treatment in the next chapter rather than a single fixed recommendation.

\section{Implications for the Remainder of This Thesis}

The stage breakdown and the global sensitivity analysis together justify the choice of parameters examined in the rest of this thesis. \texttt{spread\_max\_sp\_size} is both the highest-ranked parameter here and, as shown in Chapter~\ref{ch:parameter_tuning}, governed by a nontrivial trade-off between scheduling overhead and load imbalance, so it receives a dedicated treatment. \texttt{spread\_sort} clearly matters too, but its optimal setting is simple (sorting should remain enabled, as it already is by default for realistic inputs), so no further heuristic development is needed for it. \texttt{upsampfac} ranks low in this single-workload study, but its known coarse, two-valued default heuristic leaves a large, unaddressed middle ground; Chapter~\ref{ch:sigma_selection} develops a cost model to select it properly as a function of the input. The remaining searched parameters, \texttt{modeord} and \texttt{spread\_nthr\_atomic}, contribute negligible variance in this analysis and are not investigated further. \texttt{spread\_thread} and \texttt{maxbatchsize} were excluded from the search itself, since both only affect vectorized multi-transform calls, which fall outside the scope of this thesis.

\section{Summary}

This chapter established where FINUFFT spends its time and which of its configuration parameters have the largest effect on it. Stage-level timing showed that \texttt{execute} dominates type 1 and type 2 transforms, while \texttt{setpts} becomes comparably important for type 3 transforms. A Gaussian process based sensitivity analysis further showed that \texttt{spread\_max\_sp\_size} and \texttt{spread\_sort} account for the large majority of performance variance in a representative workload, while \texttt{upsampfac} has a comparatively small global effect that is nonetheless large in specific, poorly served regions of the input space. These findings set the agenda for the following two chapters: a principled, input-dependent choice of $\sigma$ (Chapter~\ref{ch:sigma_selection}), and a heuristic for the maximum spreader subproblem size (Chapter~\ref{ch:parameter_tuning}).
