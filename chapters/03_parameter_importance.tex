\section{Stage-Level Breakdown}
\label{sec:stage_breakdown}

Every FINUFFT call proceeds through three stages, introduced in Section~\ref{sec:transform_structure}: \texttt{makeplan}, which precomputes kernel coefficients and creates the FFT plan; \texttt{setpts}, which sorts and preprocesses the nonuniform points; and \texttt{execute}, which performs the actual spreading, FFT, and deconvolution. Before deciding which configuration parameters deserve attention, it is useful to know how much of the total runtime each stage typically accounts for, since a parameter that only affects a negligible stage cannot meaningfully improve overall performance.

Using the benchmark configurations distributed with FINUFFT (covering a range of precisions, tolerances, dimensions, and both extremal values of $\sigma$), each call was timed and the three stage durations were normalised so that they summed to one. Figure~\ref{fig:stage_breakdown} shows the resulting distribution, split by transform type. For type 1 and type 2 transforms, \texttt{execute} dominates, accounting for the large majority of the total time, while \texttt{setpts} contributes a smaller but non-negligible share and \texttt{makeplan} is close to zero in almost every case. Type 3 transforms show a markedly different balance: \texttt{setpts} and \texttt{execute} contribute comparable shares, reflecting the additional preprocessing type 3 transforms require to handle nonuniform points on both sides of the transform.

\begin{figure}[ht]
    \centering

    \caption{Share of call time per stage (\texttt{makeplan}, \texttt{setpts}, \texttt{execute}) by transform type.}
    \label{fig:stage_breakdown}
\end{figure}


The parameters of Section~\ref{sec:finufft_parameters} act on different stages (Table~\ref{tab:param_stages}). The upsampling factor is the only one that reaches all three. It fixes the kernel width and the fine grid in \texttt{makeplan}, changes the number of bins the points are sorted into in \texttt{setpts}, and sets both the spreading work per point and the size of the FFT in \texttt{execute}. Sorting and the bin dimensions decide how much work the sort in \texttt{setpts} does and, through the resulting order of the points, how scattered the points of each subproblem are when \texttt{execute} spreads them. The maximum subproblem size and the atomic-update threshold act only inside the spreading stage of \texttt{execute}: the first sets the size of each subproblem's gather buffer and subgrid, and the second only how the adding step writes to the shared grid.

\section[Global Sensitivity Analysis via Gaussian-Process Optimization]{Global Sensitivity Analysis via \mbox{Gaussian-Process Optimization}}
\label{sec:gp_sensitivity}

A Gaussian-process-based Bayesian optimizer~\cite{rasmussen2006,snoek2012}, as implemented in Optuna~\cite{optuna2019}, searched the joint parameter space and determined the contribution of each configuration parameter. The search space included \texttt{spread\_max\_sp\_size} ($S_{\max}$), \texttt{spread\_sort}, \texttt{upsampfac}, \texttt{spread\_nthr\_atomic} and the two bin dimensions $b_x$ and $b_y$, sampled from the ranges given in Section~\ref{sec:problem_statement}. For each configuration, the optimizer ran the reference transform of Section~\ref{sec:workload} on all $40$ hardware threads and measured the total time of \texttt{setpts} and \texttt{execute}.

The best configuration found completed the transform in $1.643$\,s, against $2.142$\,s for the library defaults; Table~\ref{tab:gp_best} lists the parameters of both. A single trial can be favoured by noise, so both configurations were re-measured three times each on the same node, which gave the same result. The best configuration agrees with the defaults on $\sigma$ and on sorting, and both use atomic updates at this thread count, so the whole of the margin comes from the remaining two parameters: the subproblem size and the bin dimensions. The subproblem size the search settles on agrees with the sweep of Chapter~\ref{ch:parameter_tuning}, which places the minimum of the spreading stage at $S_{\max} \approx 2000$ for the same transform.

Figure~\ref{fig:gp_histogram} shows the distribution of times across all completed trials on a logarithmic axis, with both configurations of Table~\ref{tab:gp_best} marked. Most trials lie within a factor of a few of the default, and a tail of slow configurations runs past the eight-second cap at which trials were stopped.

The fANOVA percentages are estimates of how sensitive the execution time is to each parameter, not of how much each parameter can improve it. A parameter scores highly when poor choices of it are expensive, since the variance across the search space is dominated by the worst configurations, and the score says nothing about the headroom left above the library default. A low score is therefore not evidence of irrelevance: $S_{\max}$ scores low here, yet Chapter~\ref{ch:parameter_tuning} shows that it has a substantial effect on the spreading stage.

\section{Eliminated parameters}
\label{sec:eliminated_params}

Three of the performance-relevant parameters of Section~\ref{sec:finufft_parameters} have a setting that is best for every transform of realistic size, so they are fixed in the rest of this thesis rather than analysed further.

\emph{Thread count.} Every stage of \texttt{execute} and the sort in \texttt{setpts} are parallelised, so a transform large enough to give each thread several subproblems runs fastest on all hardware threads. Fewer threads pay off only for transforms so small that the cost of starting and synchronising the threads outweighs the work they share. \texttt{nthreads} is therefore set to the number of hardware threads, $40$ on the machine of Chapter~\ref{ch:methodology}.

\emph{Sorting.} Sorting accounts for $99.5\%$ of the variance in the search (Figure~\ref{fig:importance}), and always in the same direction: without it, consecutive points land far apart on the fine grid, each subgrid spans most of the grid, and spreading spills to main memory. Its cost in \texttt{setpts} is linear in the number of points and is repaid many times over in \texttt{execute}. Sorting is therefore always enabled.

\emph{Atomic-update threshold.} The threshold only selects how the adding step writes to the shared grid: under a lock below it and with atomic updates above it. A lock is faster on few threads, where it is rarely contended while atomics pay on every cell written, and atomics are faster on many threads, where the lock keeps all but one thread idle. Measured on the reference transform, the two break even between $10$ and $16$ threads, which is close to where the default threshold of $10$ already places the switch. With the thread count fixed at all $40$ hardware threads, every threshold below $40$ selects atomic updates, so its variation changes nothing, and the search confirms that it has no measurable effect on the run time (Figure~\ref{fig:importance}). The threshold is left at its default.

\subsection{The Same Parameters on the GPU}
\label{sec:eliminated_gpu}

On a GPU implementation such as cuFINUFFT~\cite{shih2021}, the choices for sorting and the thread count carry over unchanged, for reasons that are only stronger there. The atomic-update threshold does not: a GPU has no setting at which a lock is the better choice, so atomic updates are always used.

\emph{Sorting.} On the GPU each subproblem is spread into a subgrid held in shared memory (Section~\ref{sec:related_libraries}). Without sorting, the points of a subproblem are scattered across the fine grid, so the subgrid that covers them grows far beyond the size of shared memory and cannot be allocated there. Sorting is therefore always enabled.

\emph{Thread count.} A GPU hides the latency of its memory accesses by switching between many threads, which it can do only when it has enough of them. All of its threads are therefore used.

\emph{Atomic updates.} A GPU runs far more threads than a CPU, so a lock on the shared grid would be contended at all times. A lock-based implementation also requires branching, since a thread must test whether it holds the lock before it writes. The threads of a warp execute in lockstep, so when they take different branches the warp runs each branch in turn, and the threads on the other branch stall. Atomic updates avoid the branch, and are therefore always used.
