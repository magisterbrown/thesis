\chapter{Background}
\label{ch:background}

This chapter introduces the background the rest of the thesis builds on. It
first describes the nonuniform fast Fourier transform and how FINUFFT divides it
into stages, with particular attention to the spreading stage. It then reviews
related work on choosing NUFFT parameters, on organising the spreading stage and
on explaining performance, and closes with the research gap.

\section{Nonuniform Fast Fourier Transforms}

The standard Discrete Fourier Transform (DFT) operates on uniformly sampled data. Many practical applications, however, involve data sampled at irregular (nonuniform) locations. The Nonuniform Fast Fourier Transform (NUFFT) generalizes the FFT to handle such data efficiently.

Three types of NUFFT are commonly distinguished, according to which side of the transform is nonuniform. Write $M$ for the number of nonuniform points and $N$ for the number of uniform modes.
\begin{itemize}
    \item \textbf{Type 1 (nonuniform to uniform):} given strengths $c_j$ at nonuniform locations $x_j$, evaluate the Fourier coefficients $f_k = \sum_{j=1}^{M} c_j e^{\pm i k \cdot x_j}$ on a uniform grid of modes $k$.
    \item \textbf{Type 2 (uniform to nonuniform):} the adjoint operation. Given coefficients $f_k$ on a uniform grid of modes, evaluate the Fourier series $c_j = \sum_k f_k e^{\pm i k \cdot x_j}$ at nonuniform target locations $x_j$.
    \item \textbf{Type 3 (nonuniform to nonuniform):} given strengths at nonuniform locations $x_j$, evaluate at nonuniform target frequencies $s_k$, with neither side lying on a grid.
\end{itemize}

The direct evaluation of any of these costs $O(MN)$. The NUFFT reduces this to $O(M + N \log N)$ by moving the problem onto a uniform grid where an FFT can be used. Each nonuniform point is first convolved with a smooth, rapidly decaying kernel $\varphi$ of width $w$ grid cells, which spreads its contribution over the $w^d$ surrounding cells. This grid is finer than the output grid by an upsampling factor $\sigma > 1$, so that the aliasing caused by the convolution falls outside the band of interest. After the FFT, the convolution is undone by dividing each mode by the kernel's Fourier transform, a stage called deconvolution. The requested tolerance $\varepsilon$ and the upsampling factor $\sigma$ together determine the kernel width $w$.

\subsection{Structure of a transform}
\label{sec:transform_structure}

FINUFFT~\cite{barnett2019} exposes this algorithm through three calls, and the parameters studied in this thesis act on different ones. A transform is created with \texttt{makeplan}, given its nonuniform points with \texttt{setpts}, and evaluated with \texttt{execute}. This split lets several transforms that share the same points reuse one plan.

\texttt{makeplan} does no work on the data, but fixes every quantity the later stages depend on. From the tolerance and the upsampling factor it selects the kernel width $w$ and precomputes the coefficients used to evaluate the kernel quickly. It also chooses the size of the fine grid, evaluates the kernel's Fourier series for the later deconvolution, and creates the FFT plan.

\texttt{setpts} accepts the nonuniform points, and its main task is to sort them. In recent versions it also revisits the choice of upsampling factor once the point density is known.

\texttt{execute} performs the transform in three phases. For a type 1, it spreads the nonuniform strengths onto the fine grid, transforms that grid with the FFT, and deconvolves each mode. A type 2 runs the same phases in reverse: it scales the uniform inputs by the reciprocal kernel coefficients, applies the FFT, and interpolates the values at the nonuniform points from the fine grid.

\subsection{Type 3 as a composition of types 1 and 2}

A type 3 transform has nonuniform points on both sides, so neither side lies on a grid. FINUFFT computes it by chaining the other two types~\cite{barnett2019}: a type 1 produces an intermediate uniform grid, and an inner type 2 evaluates that grid at the output frequencies. Most of the extra work is done in \texttt{setpts}, where the inner plan and the deconvolution factors for each target are built.

\subsection{The spreading stage}

The spreading stage is the one this thesis is most concerned with, and it is not a single loop. The sorted points are divided into subproblems, and each thread processes one subproblem at a time into a private buffer called a subgrid. This prevents threads from contending for the shared output grid. Processing a subproblem has three steps. \emph{Gathering} copies the subproblem's coordinates and strengths into contiguous scratch space. \emph{Spreading} evaluates the kernel around each point and accumulates the result into the subgrid. \emph{Adding} accumulates the finished subgrid into the shared grid, wrapping at the periodic boundary. Interpolation, the type-2 direction, has no adding step, since it reads from the grid rather than writing to it. Chapter~\ref{ch:parameter_tuning} shows that the three steps respond to the spreader's parameters in different, often opposing, directions.

\section{Related Work}
\label{sec:related_work}

Work related to this thesis falls into three groups: approaches to choosing the configuration of an FFT or NUFFT library, the ways NUFFT implementations organise spreading, and the tools used to explain where a program spends its time. This section reviews each group, describes the FFT library used in this thesis, and closes with the research gap.

\subsection{Choosing a configuration}
\label{sec:related_tuning}

FFT and NUFFT libraries choose their configuration in one of two ways. Planner-based libraries measure. FFTW~\cite{frigo2005} times candidate plans on the machine it runs on and keeps the fastest, so its choice adapts to the hardware. gNUFFTW~\cite{ou2017}, the closest prior work on NUFFT configuration, applies the same approach to NUFFTs on GPUs. Both pay a planning time that can far exceed the time of a single transform, which is repaid only when a plan is reused many times. NFFT3~\cite{keiner2009}, a widely used CPU alternative to FINUFFT, takes the opposite approach, as does FINUFFT itself: when the user sets nothing, fixed defaults apply. NFFT3 exposes more of its parameters than FINUFFT, but it likewise leaves the trade-offs between them to the user.

That there is anything to choose at all follows from the analysis of the spreading kernel. Beatty et al.~\cite{beatty2005} showed that the conventional upsampling factor of two is not required. Instead, a whole family of pairs of upsampling factor $\sigma$ and kernel width $w$ reaches any given accuracy, because a smaller factor can be compensated by a wider kernel. For the kernel that FINUFFT uses, Barnett~\cite{barnett2021aliasing} proved that the aliasing error decays exponentially in the kernel width, at a rate set by the upsampling factor. FINUFFT uses this relation to derive $w$ from the tolerance and $\sigma$. As a result, every $\sigma$ in the interval studied in Chapter~\ref{ch:sigma_selection} reaches the requested accuracy, and the values differ only in cost.

gNUFFTW searches exactly this family, and its findings show how much the choice matters. It tunes the oversampling ratio $\alpha$ and kernel width $W$, which correspond to $\sigma$ and $w$ here. A tuned ratio improved performance by up to an order of magnitude over the fixed ratios $1.125$ and $2$, whereas FINUFFT's rule chooses only between $1.25$ and $2$. The best ratio depended on how the run time is split between spreading and the FFT: it was close to $2$ when spreading dominated and fell as spreading became cheaper. In gNUFFTW this split is driven by how strongly the samples are undersampled, which in the terms of this thesis corresponds to the point density $\rho$. gNUFFTW's finding is therefore that the best upsampling factor falls with density, the trade-off that Chapter~\ref{ch:sigma_selection} models for FINUFFT. gNUFFTW, however, locates this optimum by search on a single GPU and does not model it.

\subsection{Organising the spreading stage}
\label{sec:related_libraries}

NUFFT implementations organise spreading around two units: a sorting unit that groups nearby points, and a work unit that one processor spreads into a private buffer. They differ in whether the two units are the same. In gpuNUFFT~\cite{knoll2014gpunufft}, one of the implementations gNUFFTW chooses among, a single unit called the sector plays both roles. A sector is a cube of the fine grid: samples are sorted by sector, and each sector is spread by one processor into shared memory. The sector width therefore fixes both the sort granularity and the size of the region each processor writes. FINUFFT, in contrast, separates the two roles. Its bins only group the points, and a subproblem is a run of up to $S_{\max}$ sorted points that may span many bins. The size of a subgrid therefore depends on both the bin dimensions and $S_{\max}$.

cuFINUFFT~\cite{shih2021}, the GPU counterpart of FINUFFT, keeps this separation, with a limit on the points per subproblem that plays the role of $S_{\max}$. The parameters studied in Chapter~\ref{ch:parameter_tuning} therefore have direct counterparts on the GPU. The constraint on them differs, however. On the GPU the padded subgrid must fit in shared memory, which sets a hard limit on the bin dimensions. On the CPU, a working set that spills from a cache is only slower. Despite their effect on performance, these structural parameters have received little attention. gNUFFTW keeps the sector width at the recommended value of $8$ and leaves it out of its search. In the released FINUFFT, the bin dimensions are compile-time constants that cannot be changed at all.

\subsection{FFT backend}
\label{sec:related_ducc}

FINUFFT can be built against FFTW, but in this thesis it uses the DUCC library~\cite{ducc} as its FFT backend. DUCC derives its central algorithms from FFTPACK~\cite{fftpack}. The textbook radix-2 FFT~\cite{cooley1965} requires the length to be a power of two. FFTPACK instead factorises the length, $N = p_1 p_2 \cdots p_k$, and makes one pass over the data for each factor. This mixed-radix approach handles any length, but a pass for a factor $p$ costs roughly $p$ operations per element, so large prime factors are expensive. DUCC handles them with Bluestein's algorithm~\cite{bluestein1970}, which keeps the cost at $\mathcal{O}(N \log N)$ for every length. A length with a large prime factor is nevertheless several times slower than a nearby length built from small primes. This is why FINUFFT rounds each fine-grid length up to the next even product of $2$, $3$ and $5$.

\subsection{Explaining performance}
\label{sec:related_perf}

Explaining why a configuration is fast requires seeing where the time goes, and hardware performance counters make this possible. The counters~\cite{intelsdm} are a small set of processor registers that count events, such as cache misses, as a program runs. Which events are available varies between processors, and not all of them are accurate, so they must be chosen with care. The operating system saves and restores the counters as threads are scheduled, which allows counts to be attributed to a single process. On Linux they are read through the \texttt{perf} tool~\cite{perf}, whose features and overhead Weaver~\cite{weaver2013} documents.

Counters alone show how many events occurred, not why a parallel program falls short of its ideal speed-up. Eyerman et al.~\cite{eyerman2012} split that shortfall into one component per cause. The causes include synchronisation, interference between threads in the shared cache and in memory, and imbalance in the work given to each thread. Several of these leave distinguishable traces in \texttt{perf}. Time lost to synchronisation appears as cycles inside the routine that takes the lock or performs the atomic update. Interference appears in the miss counters of the cache level concerned, which can be compared between runs on one thread and on many. Imbalance appears in neither. Instead, it shows as a difference between wall time and cycle count, because a thread that has run out of work retires no cycles while the phase continues.

Whether a step is limited by computation or by data movement is described by the Roofline model of Williams et al.~\cite{williams2009roofline}. The model characterises a kernel by its arithmetic intensity $I$, the number of floating-point operations it performs per byte it moves, and bounds its attainable performance by
\begin{equation}
    P \le \min\left(P_{\text{peak}},\; I \cdot B\right),
    \label{eq:roofline}
\end{equation}
where $P_{\text{peak}}$ is the peak floating-point rate of the processor and $B$ the bandwidth of the memory the data comes from. At low intensity a kernel is memory-bound and its speed is set by bandwidth. At high intensity it is compute-bound. Each level of the cache hierarchy has its own bandwidth, so a kernel whose working set spills from one level to the next becomes slower without its arithmetic changing. The stages studied in this thesis sit on different sides of this bound. The adding step does little arithmetic per cell written, so it is memory-bound. Spreading evaluates the kernel $w^d$ times per point, so it is compute-bound as long as the region it writes stays in cache.

\subsection{Research gap}
\label{sec:related_gap}

Existing work therefore either finds a fast configuration by measurement or relies on fixed defaults. Search-based tuners such as FFTW and gNUFFTW adapt to the hardware, but they do not explain their choice, so the search must be repeated for every new input and machine. Libraries such as NFFT3 and FINUFFT apply the same defaults everywhere. The analysis of Beatty et al.\ and Barnett establishes which configurations are valid, but not which of them is fastest. The structural parameters of the spreader have been left out of the search altogether. What is missing is an explanation of how the cost of each stage depends on each parameter and on the machine. No study to date has modelled how the parameters of a CPU NUFFT shift cost between its stages, or used such models to choose parameter values before a transform runs. This thesis addresses that gap for FINUFFT.
