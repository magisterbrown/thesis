\chapter{Background}
\label{ch:background}

This chapter introduces the background the rest of the thesis builds on. It
first describes the nonuniform fast Fourier transform and how FINUFFT structures
it into stages, with particular attention to the spreading stage that most of
the parameters studied here act on. It then reviews related work: earlier
approaches to choosing NUFFT parameters, other NUFFT libraries, the FFT library
used as a backend, and the tools and models used to analyse performance.

\section{Nonuniform Fast Fourier Transforms}

The standard Discrete Fourier Transform (DFT) operates on uniformly sampled data. Many practical applications, however, involve data sampled at irregular (nonuniform) locations. The Nonuniform Fast Fourier Transform (NUFFT) generalizes the FFT to handle such data efficiently.

Three types of NUFFT are commonly distinguished, according to which side of the transform is nonuniform. Write $M$ for the number of nonuniform points and $N$ for the number of uniform modes.
\begin{itemize}
    \item \textbf{Type 1 (nonuniform to uniform):} given strengths $c_j$ at nonuniform locations $x_j$, evaluate the Fourier coefficients $f_k = \sum_{j=1}^{M} c_j e^{\pm i k \cdot x_j}$ on a uniform grid of modes $k$.
    \item \textbf{Type 2 (uniform to nonuniform):} the adjoint operation. Given coefficients $f_k$ on a uniform grid of modes, evaluate the Fourier series $c_j = \sum_k f_k e^{\pm i k \cdot x_j}$ at nonuniform target locations $x_j$.
    \item \textbf{Type 3 (nonuniform to nonuniform):} given strengths at nonuniform locations $x_j$, evaluate at nonuniform target frequencies $s_k$, with neither side lying on a grid.
\end{itemize}

The direct evaluation of any of these costs $O(MN)$. The NUFFT reduces this to $O(M + N \log N)$ by moving the problem onto a uniform grid where an FFT can be used. Because the nonuniform points do not lie on that grid, they are first convolved with a smooth, rapidly decaying kernel $\varphi$ of width $w$ grid cells, which spreads each point's contribution over the $w^d$ cells surrounding it. The grid used for this is finer than the output grid by an upsampling factor $\sigma > 1$, so that the aliasing introduced by the convolution falls outside the band of interest. The convolution is then undone in Fourier space by dividing each mode by the kernel's Fourier transform, a stage referred to as deconvolution. The accuracy of the result is controlled by the requested tolerance $\varepsilon$, which together with $\sigma$ determines the kernel width $w$: a wider kernel decays faster in Fourier space and therefore leaves less aliasing to correct.

\subsection{Structure of a transform}
\label{sec:transform_structure}

FINUFFT~\cite{barnett2019} exposes this algorithm through a three-call interface, and it is worth setting out what each call does, since the parameters studied in this thesis act on different ones. A transform is created with \texttt{makeplan}, given its nonuniform points with \texttt{setpts}, and evaluated with \texttt{execute}; the split exists so that several transforms sharing the same points can reuse one plan, and so that the substantial precomputation each stage performs is not repeated.

\texttt{makeplan} does no work on the data at all, but fixes every quantity the later stages depend on. From the requested tolerance and the upsampling factor it selects the kernel width $w$ and the kernel's shape parameter, then precomputes the piecewise-polynomial coefficients used to evaluate the kernel quickly at run time. It chooses the size of the fine grid, rounding it up to a length the FFT library handles efficiently, evaluates the Fourier series of the kernel on that grid for the later deconvolution, and creates the FFT plan itself.

\texttt{setpts} accepts the nonuniform points. Its principal task is to sort them, which is discussed in detail below, but in recent versions it also revisits the choice of upsampling factor once the point density is known, and repeats the parts of the planning stage that depend on it if the choice changes.

\texttt{execute} performs the transform in three phases. For a type 1 these are spreading the nonuniform strengths onto the fine grid, transforming that grid with the FFT, and deconvolving each mode while shuffling it into the requested output ordering. A type 2 also runs three phases: the uniform inputs are amplified by the reciprocal kernel coefficients, an FFT produces the fine grid, and the values at the nonuniform modes are then interpolated from it. A type 3 is not a third algorithm but a composition of the first two, and is described separately below.

\subsection{Type 3 as a composition of types 1 and 2}

A type 3 transform process non uniform input points and outputs non uniform modes in the frequency domain. FINUFFT implementation resolves this~\cite{barnett2019} by chaining the other two types: a type 1 to produce a uniform grid of coefficients as an intermediate, and a type 2 already consumes one, so the grid appears only inside the composition. \texttt{execute} multiplies the input strengths by a phase that recentres the source points, spreads them onto an internal fine grid exactly as a type 1 does, evaluates that grid at the output frequencies with an inner type-2 plan built during \texttt{makeplan}, and finally divides each output by the kernel's Fourier transform at its own target frequency. The internal fine grid is sized by the widths of the intervals containing the sources and the targets and a much larger share of the work falls in \texttt{setpts}, where the inner plan and the per-target deconvolution factors are built.

\subsection{The spreading stage}

The spreading stage is the one this thesis is most concerned with, and it is not a single loop. The sorted points are divided into subproblems, each processed by one thread into a private buffer called a subgrid, so that threads do not contend for the shared output grid. Processing a subproblem has three stages: \emph{gathering}, which copies the subproblem's coordinates and strengths out of the sorted arrays into contiguous scratch space; \emph{spreading kernel evaluation}, which evaluates the kernel around each point and accumulates it into the subgrid; and \emph{adding}, which accumulates the finished subgrid back into the shared output grid, wrapping at the periodic boundary. Interpolation, the type-2 direction, has no adding stage, since it reads from the grid rather than writing to it. Chapter~\ref{ch:parameter_tuning} shows that these three stages respond to the spreader's parameters in different, and often opposing, directions.

%Processing a single subproblem during \texttt{execute} consists of three stages. \emph{Gathering} loads the coordinates and strengths of that subproblem's assigned points into a local buffer and allocates the local subgrid they will be spread onto. \emph{Spreading kernel evaluation} then accumulates each point's contribution into that local subgrid, appkklying the spreading kernel over the $w^d$ neighbourhood of cells around each point. \emph{Adding} (\texttt{add\_wrapped\_subgrid}) finally writes the finished local subgrid back into the shared global fine grid.

\section{Related Work}
\label{sec:related_work}

Work related to this thesis falls into three groups: approaches to choosing the configuration of an FFT or NUFFT library, the structures that NUFFT implementations use to organise the spreading stage, and the tools and models used to explain where a program spends its time. This section reviews each group in turn, describes the FFT library used throughout the thesis, and closes with the gap that the thesis addresses.

\subsection{Choosing a configuration}
\label{sec:related_tuning}

FFT and NUFFT libraries choose their configuration in one of two ways. Planner-based libraries measure. FFTW~\cite{frigo2005} assembles each transform from interchangeable algorithmic steps, times the candidate plans on the machine it runs on and keeps the fastest, so that its choice adapts to the cache hierarchy and instruction set of the hardware. gNUFFTW~\cite{ou2017}, the closest prior work on NUFFT configuration, applies the same approach to NUFFTs on GPUs: during planning it runs candidate implementations and parameter values and keeps the fastest. Both adapt to the hardware, but both pay a planning time that can far exceed the time of a single transform and is repaid only when a plan is reused many times. NFFT3~\cite{keiner2009}, a widely used CPU alternative to FINUFFT, and FINUFFT itself take the opposite approach: when the user sets nothing, fixed defaults apply. NFFT3 exposes more of its parameters than FINUFFT -- the window function, the oversampling factor and the cut-off that plays the role of the kernel width -- but, like FINUFFT, leaves the trade-offs between them to the user.

That there is anything to choose at all follows from the analysis of the spreading kernel. Beatty et al.~\cite{beatty2005} showed that the conventional upsampling factor of two is not required: a whole family of pairs of upsampling factor $\sigma$ and kernel width $w$ reaches any given accuracy, since a smaller factor can be compensated by a wider kernel, and they gave the maximum aliasing amplitude as the measure that decides which pairs qualify. For the exponential-of-semicircle kernel that FINUFFT uses, Barnett~\cite{barnett2021aliasing} bounded the aliasing error rigorously and showed that it decays exponentially in the kernel width, at a rate set by the upsampling factor. FINUFFT relies on this relation when it derives $w$ from the requested tolerance and $\sigma$, and it is what makes every $\sigma$ in the interval studied in Chapter~\ref{ch:sigma_selection} a valid choice at a given accuracy, differing only in cost.

gNUFFTW searches exactly this family, and its findings show how much the choice matters. It tunes the oversampling ratio $\alpha$ and the kernel width $W$, which correspond to $\sigma$ and $w$ here, and reports that a tuned ratio improves performance by up to an order of magnitude over fixed values, outperforming both fixed ratios it is compared against, $1.125$ and $2$. FINUFFT's rule, in comparison, chooses only between $1.25$ and $2$. The optimal ratio in gNUFFTW depends on how the run time is split between spreading and the FFT: it is close to $2$ when spreading dominates and falls as spreading becomes cheaper. In gNUFFTW this split is moved by the acceleration factor $R$, the degree to which the samples are undersampled relative to the Nyquist rate. Since the number of samples falls in proportion to $1/R$ while the grid stays the same, a larger $R$ corresponds to a smaller point density $\rho$ in the terms of this thesis, and gNUFFTW's finding is therefore that the optimal upsampling factor falls with density. This is the trade-off that Chapter~\ref{ch:sigma_selection} models for FINUFFT. gNUFFTW, however, locates the optimum by search, with all measurements taken on a single Tesla K40 GPU, and does not model it.

\subsection{Organising the spreading stage}
\label{sec:related_libraries}

NUFFT implementations organise spreading around two units, a sorting unit that groups nearby points and a work unit that one processor spreads into a private buffer, but they differ in whether the two are tied together. In gpuNUFFT, one of the implementations gNUFFTW chooses among, a single unit, the sector, plays both roles. A sector is a cube of the fine grid: the samples are sorted by the sector they fall in, and each sector is spread by one processor into fast shared memory, padded by $W/2$ on every side, before the result is written once to the global grid. The sector width therefore fixes both the sort granularity and the size of the region each processor writes, independently of how many samples the sector holds; a limit on the samples per sector only splits a full sector into virtual sectors to divide the load. FINUFFT, in contrast, separates the two roles. Its bins only group the points, and a subproblem is a contiguous run of up to $S_{\max}$ sorted points that may span many bins, so the size of its subgrid depends on both the bin dimensions and $S_{\max}$, through the formulas of Chapter~\ref{ch:parameter_tuning}.

cuFINUFFT~\cite{shih2021}, the GPU counterpart of FINUFFT, keeps this separation: the points are sorted into bins, and each subproblem accumulates the points of one region into a padded subgrid in shared memory, with a separate limit on the points per subproblem playing the role of $S_{\max}$. The parameters studied in Chapter~\ref{ch:parameter_tuning} therefore have direct counterparts on the GPU. The constraint on them differs, however. On the GPU the padded subgrid must fit in shared memory, which bounds the bin dimensions as a hard limit, whereas on the CPU a working set that spills from a cache is only slower. Despite their effect on performance, these structural parameters have received little attention: gNUFFTW keeps the sector width at the value of $8$ recommended for three-dimensional transforms and leaves it out of its search, giving no reason beyond that recommendation, and in the released FINUFFT the bin dimensions are compile-time constants that cannot be changed at all.

\subsection{FFT backend}
\label{sec:related_ducc}

FINUFFT can be built against FFTW, but in this thesis it uses Martin Reinecke's DUCC library~\cite{ducc} as its FFT backend. DUCC is an evolution of the pocketfft library, whose central algorithms derive from Swarztrauber's FFTPACK~\cite{fftpack}. FFTPACK improves on the textbook FFT~\cite{cooley1965} in one respect that matters here. The textbook radix-2 algorithm requires the length to be a power of two, because it works by halving the transform again and again. FFTPACK instead factorises the length, $N = p_1 p_2 \cdots p_k$, and makes one pass over the data for each factor, the pass for a factor $p$ computing $N/p$ transforms of length $p$. This is the mixed-radix generalisation of the Cooley--Tukey algorithm~\cite{cooley1965}. Any length can be handled this way, but the passes are not equally cheap: a pass costs roughly $p$ operations per element, so a large prime factor is expensive. DUCC handles such a factor with Bluestein's algorithm~\cite{bluestein1970}, which re-expresses a transform of any length as a convolution evaluated with FFTs of a larger, smooth length. The transform therefore stays $\mathcal{O}(N \log N)$ for every length, but a length with a large prime factor is still several times slower than a nearby length built from small primes. This is why FINUFFT rounds each fine-grid length up to the next even product of $2$, $3$ and $5$.

\subsection{Explaining performance}
\label{sec:related_perf}

Explaining why a configuration is fast requires seeing where the time goes, and hardware performance counters make this possible. The counters~\cite{intelsdm} are a small set of architectural registers that count events as the processor executes: in general between two and eight programmable ones per core, alongside a few fixed ones. Which events they can count varies considerably between processors and vendors, and some processors expose hundreds of them with uneven documentation, so separating the useful and accurate events from those that are broken or measure architectural minutiae takes care. The registers are privileged, so the operating system programs them on the user's behalf and saves and restores them as threads are scheduled, which allows counts to be attributed to a single process. On Linux they are read through the \texttt{perf\_event} interface and the \texttt{perf} tool~\cite{perf}, whose features and overhead Weaver~\cite{weaver2013} documents.

Counters alone show how many events occurred, not why a parallel program falls short of its ideal speed-up. Eyerman et al.~\cite{eyerman2012} split that shortfall into components, one for each cause: spinning on locks and barriers, yielding, interference between threads in the last-level cache and in main memory, cache coherency traffic, imbalance between the work given to each thread, and the overhead of parallelisation itself. Several of these leave distinguishable traces in \texttt{perf}. Because each sample is attributed to the function executing when it is taken, time lost to synchronisation appears as cycles inside the routine that takes the lock or performs the atomic update, rather than as time missing from the total. Interference in the shared cache and in memory appears in the fill and miss counters of the level concerned, which can be compared between a run on one thread and a run on many. Imbalance appears in neither, but is visible in the difference between the two measures: a thread that has run out of work retires no cycles, so idle time lengthens the wall time of a phase while leaving its cycle count unchanged. Coherency traffic and parallelisation overhead are not separated in this thesis.

Whether a step is limited by computation or by the movement of data is described by the Roofline model of Williams et al.~\cite{williams2009roofline}. The model characterises a kernel by its arithmetic intensity $I$, the number of floating-point operations it performs per byte it moves to or from memory, and bounds its attainable performance by
\begin{equation}
    P \le \min\left(P_{\text{peak}},\; I \cdot B\right),
    \label{eq:roofline}
\end{equation}
where $P_{\text{peak}}$ is the peak floating-point rate of the processor and $B$ the bandwidth of the memory the data comes from. Plotted against $I$ on logarithmic axes, the bound has the shape of a roof: a slanted part at low intensity, where a kernel is memory-bound and its speed is set by bandwidth, and a flat part at high intensity, where it is compute-bound; the two meet at the ridge point $I = P_{\text{peak}}/B$. Since each level of the cache hierarchy has its own bandwidth, the hierarchical form of the model draws one slanted roof per level, and a kernel whose working set spills from one level to the next drops from a higher roof to a lower one without its arithmetic changing. The stages of a transform studied in this thesis sit on different parts of this roof, and the parameters move them between roofs: the adding stage writes every cell of a subgrid with little arithmetic per cell and is memory-bound, while spreading evaluates the kernel $w^d$ times per point and is compute-bound for as long as the region it writes stays in cache.

\subsection{Research gap}
\label{sec:related_gap}

Existing work therefore either finds a fast configuration by measurement or relies on fixed defaults. Search-based tuners such as FFTW and gNUFFTW adapt to the hardware but do not explain their choice, so it must be repeated for every new input and machine, while libraries such as NFFT3 and FINUFFT apply the same defaults everywhere. The analysis of Beatty et al.\ and Barnett establishes which configurations are valid, but not which of them is fastest, and the structural parameters of the spreader have been left out of the search altogether. What is missing is an explanation of how the cost of each stage depends on each parameter and on the machine. The tools for explaining performance exist, but no study to date has applied them to model how the parameters of a CPU NUFFT shift cost between its stages, or used such models to choose parameter values before a transform runs. This thesis addresses that gap for FINUFFT.
