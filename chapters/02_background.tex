\section{Nonuniform Fast Fourier Transforms}

The standard Discrete Fourier Transform (DFT) operates on uniformly sampled data. Many practical applications, however, involve data sampled at irregular (nonuniform) locations. The Nonuniform Fast Fourier Transform (NUFFT) generalizes the FFT to handle such data efficiently.

Three types of NUFFT are commonly distinguished, according to which side of the transform is nonuniform. Write $M$ for the number of nonuniform points and $N$ for the number of uniform modes.
\begin{itemize}
    \item \textbf{Type 1 (nonuniform to uniform):} given strengths $c_j$ at nonuniform locations $x_j$, evaluate the Fourier coefficients $f_k = \sum_{j=1}^{M} c_j e^{\pm i k \cdot x_j}$ on a uniform grid of modes $k$.
    \item \textbf{Type 2 (uniform to nonuniform):} the adjoint operation. Given coefficients $f_k$ on a uniform grid of modes, evaluate the Fourier series $c_j = \sum_k f_k e^{\pm i k \cdot x_j}$ at nonuniform target locations $x_j$.
    \item \textbf{Type 3 (nonuniform to nonuniform):} given strengths at nonuniform locations $x_j$, evaluate at nonuniform target frequencies $s_k$, with neither side lying on a grid.
\end{itemize}

The direct evaluation of any of these costs $O(MN)$. The NUFFT reduces this to $O(M + N \log N)$ by moving the problem onto a uniform grid where an FFT can be used. Because the nonuniform points do not lie on that grid, they are first convolved with a smooth, rapidly decaying kernel $\varphi$ of width $w$ grid cells, which spreads each point's contribution over the $w^d$ cells surrounding it. The grid used for this is finer than the output grid by an upsampling factor $\sigma > 1$, so that the aliasing introduced by the convolution falls outside the band of interest. The convolution is then undone in Fourier space by dividing each mode by the kernel's Fourier transform, a step referred to as deconvolution. The accuracy of the result is controlled by the requested tolerance $\varepsilon$, which together with $\sigma$ determines the kernel width $w$: a wider kernel decays faster in Fourier space and therefore leaves less aliasing to correct.

\subsection{Structure of a transform}
\label{sec:transform_structure}

FINUFFT~\cite{barnett2019} exposes this algorithm through a three-call interface, and it is worth setting out what each call does, since the parameters studied in this thesis act on different ones. A transform is created with \texttt{makeplan}, given its nonuniform points with \texttt{setpts}, and evaluated with \texttt{execute}; the split exists so that several transforms sharing the same points can reuse one plan, and so that the substantial precomputation each stage performs is not repeated.

\texttt{makeplan} does no work on the data at all, but fixes every quantity the later stages depend on. From the requested tolerance and the upsampling factor it selects the kernel width $w$ and the kernel's shape parameter, then precomputes the piecewise-polynomial coefficients used to evaluate the kernel quickly at run time. It chooses the size of the fine grid, rounding it up to a length the FFT library handles efficiently, evaluates the Fourier series of the kernel on that grid for the later deconvolution, and creates the FFT plan itself.

\texttt{setpts} accepts the nonuniform points. Its principal task is to sort them, which is discussed in detail below, but in recent versions it also revisits the choice of upsampling factor once the point density is known, and repeats the parts of the planning stage that depend on it if the choice changes.

\texttt{execute} performs the transform in three phases. For a type 1 these are spreading the nonuniform strengths onto the fine grid, transforming that grid with the FFT, and deconvolving each mode while shuffling it into the requested output ordering. A type 2 runs the same three phases in reverse: the modes are amplified by the reciprocal kernel coefficients, an inverse FFT produces the fine grid, and the values at the nonuniform points are then interpolated from it. A type 3 is not a third algorithm but a composition of the first two, and is described separately below.

\subsection{Type 3 as a composition of types 1 and 2}

The difficulty with a type 3 transform is that neither side lies on a grid, so there is no FFT to place in the middle. FINUFFT resolves this~\cite{barnett2019} by observing that a type 1 already produces a uniform grid of coefficients as an intermediate, and a type 2 already consumes one: chaining them evaluates nonuniform sources at nonuniform targets, with the uniform grid appearing only inside the composition and never being the answer to anything the user asked.

Concretely, \texttt{execute} performs four steps. First the input strengths are multiplied by a precomputed phase, which realises the shift that recentres the source points and so keeps the fine grid as small as possible. Second, those shifted strengths are spread onto an internal fine grid with the same kernel and the same subproblem machinery a type 1 uses; this is the type-1 half, stopping short of its FFT. Third, an inner type-2 plan, created during \texttt{makeplan} and stored inside the outer plan, evaluates that grid at the nonuniform output frequencies; the FFT and the interpolation that a type 2 performs both happen here, so the middle FFT of a type 1 has effectively been replaced by an entire type-2 transform. Fourth, each output value is divided by the kernel's Fourier transform evaluated at its own target frequency, together with the phase that undoes the frequency shift.

The two deconvolutions therefore differ in kind, which is the one place the composition is not simply a type 1 followed by a type 2. A type 1 divides by a kernel Fourier series precomputed once on a uniform mode grid, which is why \texttt{makeplan} can evaluate it in advance. A type 3 must divide by the Fourier transform of the kernel at target frequencies that are not on any grid, so the correction is computed for each target by direct quadrature of the kernel against the corresponding exponential.

Two consequences follow for performance, and they explain why type 3 behaves differently from the other two in the stage breakdown of Chapter~\ref{ch:parameter_importance}. The size of the internal fine grid is set by the product of the widths of the intervals containing the sources and the targets, rather than by a mode count the user chose, which is why the shifts in the first and fourth steps matter: they shrink both widths and hence the grid. And a much larger share of the total work falls in \texttt{setpts}, since that is where the inner plan is built and where the per-target deconvolution factors are computed.

\subsection{The spreading phase}

The spreading phase is the one this thesis is most concerned with, and it is not a single loop. The sorted points are divided into subproblems, each processed by one thread into a private buffer called a subgrid, so that threads do not contend for the shared output grid. Processing a subproblem has three steps: \emph{gathering}, which copies the subproblem's coordinates and strengths out of the sorted arrays into contiguous scratch space; \emph{spreading}, which evaluates the kernel around each point and accumulates it into the subgrid; and \emph{adding}, which accumulates the finished subgrid back into the shared output grid, wrapping at the periodic boundary. Interpolation, the type-2 direction, has no adding step, since it reads from the grid rather than writing to it. Chapter~\ref{ch:parameter_tuning} shows that these three steps respond to the spreader's parameters in different, and often opposing, directions.

\section{Related Work}
\label{sec:related_work}

\subsection{Parameter selection and auto-tuning}
\label{sec:related_tuning}

The closest prior work on the performance of NUFFT configuration is gNUFFTW~\cite{ou2017}, an auto-tuning library for NUFFTs on GPUs. gNUFFTW chooses a configuration by measurement: during planning it runs candidate configurations and keeps the fastest. The report tunes several parameters at once -- the choice among several implementations, and the algorithm parameters, which are the oversampling ratio $\alpha$ and the kernel width $W$ and finds that optimal $\alpha$ improves performance by up to an order of magnitude over fixed parameters. All of its measurements were taken on a single Tesla K40 GPU. What makes such a search possible in the first place is the work of Beatty et al.~\cite{beatty2005}, which defines the space it ranges over: rather than accepting the conventional oversampling ratio of two, they show that a whole family of $(\sigma, W)$ pairs reaches any given accuracy, since a smaller ratio can be compensated by a wider kernel, and they give the maximum aliasing amplitude as the measure that decides which pairs qualify. A tuner is then free to search that family for its fastest member instead of being confined to a single value.

Of these parameters, the one of interest here is the oversampling ratio $\alpha$, which is the upsampling factor $\sigma$ of Chapter~\ref{ch:sigma_selection} under another name. The report draws the following conclusions about it.
\begin{itemize}
    \item A higher $\alpha$ spaces the aliased replicas of the image further apart, so a narrower kernel suffices for a given accuracy and interpolation becomes cheaper, at the cost of a larger FFT; a lower $\alpha$ requires a wider kernel. Since many $(\alpha, W)$ pairs reach the same accuracy, the fastest one has to be found rather than read off.
    \item The optimal $\alpha$ depends on how the runtime is split between interpolation and the FFT. When interpolation dominates, the optimal ratio is close to $2$; as interpolation becomes cheaper relative to the FFT, the optimal ratio falls.
    \item A tuned $\alpha$ outperforms both fixed values it is compared against, $1.125$ and $2$, much as FINUFFT's traditional rule chooses between $1.25$ and $2$.
\end{itemize}
What moves the split between interpolation and the FFT in the report is the acceleration factor $R$, the degree to which the samples are undersampled relative to the Nyquist rate. A fully sampled pattern has $R = 1$ and an undersampled one $R > 1$, and the number of samples $M$ falls in proportion to $1/R$ while the size of the image, and therefore of the fine grid, stays the same. In the terms of this thesis, where the density is $\rho = M / \tilde{N}$ points per fine-grid cell, a larger $R$ is therefore a proportionally smaller $\rho$. Read this way, the report's finding is that the optimal oversampling ratio falls as density falls: at high density there are many points to spread and interpolation dominates, while at low density there are few, the cost of the FFT is unchanged, and it is the FFT that decides. This is the same trade-off that Chapter~\ref{ch:sigma_selection} models for FINUFFT.

The second parameter with a counterpart in this thesis is the sector width of gpuNUFFT, one of the implementations gNUFFTW chooses among. A sector is a cube of the fine grid, and in gpuNUFFT it serves two purposes at once. It is the sorting unit: during planning the samples are sorted by the sector they fall in, which is what FINUFFT's bins do. It is also the work unit: each sector is assigned to one processor, whose samples are accumulated in fast shared memory, padded by $W/2$ on every side so that samples near the edge can reach neighbouring grid points, before the result is written once to the global grid, which is what a FINUFFT subproblem and its subgrid do. The sector width therefore fixes the sort granularity and the size of the region each processor writes into together, and that size does not depend on how many samples the sector holds. FINUFFT separates the two. Its bins only group the points, and a subproblem is a contiguous run of up to $S_{\max}$ sorted points that may span many bins, so the size of its subgrid depends on both the bin size and $S_{\max}$, through the formulas of Chapter~\ref{ch:parameter_tuning}. gpuNUFFT does have a counterpart to $S_{\max}$, in that it splits a sector into additional virtual sectors once it holds more than some number of samples, but this only divides the load among more processors; it is the sector width alone that sets the size of the region written.

The report keeps the sector width at the value of $8$ recommended for three-dimensional transforms and does not include it in the search. It gives no reason beyond that recommendation.


\subsection{FFT Backend}
\label{sec:related_ducc}

Martin Reinecke's DUCC library~\cite{ducc} is used as FFT backend in this thesis. It provides the FFT that FINUFFT uses throughout this thesis, an evolution of the pocketfft library used by NumPy and SciPy whose central algorithms derive from Swarztrauber's FFTPACK~\cite{fftpack}. FFTPACK improves on the textbook FFT~\cite{cooley1965} in one respect that matters here. The textbook radix-2 algorithm requires the length to be a power of two, because it works by halving the transform again and again. FFTPACK instead factorises the length, $N = p_1 p_2 \cdots p_k$, and makes one pass over the data for each factor, the pass for a factor $p$ computing $N/p$ transforms of length $p$. Any length can be handled this way, but the passes are not equally cheap: a pass costs roughly $p$ operations per element, so a large prime factor is expensive, and a prime length, which has only a single factor, costs on the order of $N^2$. FFTPACK is therefore most efficient when the length is a product of small primes. This is what lets FINUFFT round each fine-grid length only up to the next even product of $2$, $3$ and $5$.  

\subsection{Performance analysis}
\label{sec:related_perf}

The cycle counts and hardware event counts used throughout this thesis are read through the Linux \texttt{perf\_event} interface, which expose the processor's performance counters to user space, and whose features and overhead Weaver~\cite{weaver2013} documents. The counters themselves are a small set of architectural registers that count events as the processor executes, and only a handful are available at a time: in general between two and eight programmable ones per core, alongside a few fixed ones. Which events they can be told to count varies considerably between processors and vendors, and some processors expose hundreds of them, with uneven documentation, so that separating the useful and accurate events from those that are broken or measure architectural minutiae takes care. The registers are privileged, so the operating system programs them on the user's behalf and saves and restores them as threads are scheduled, which is what allows counts to be attributed to a single process.

Eyerman et al.~\cite{eyerman2012} split the speedup a multi-threaded program achieves into components that together account for its distance from the ideal, one for each cause: time spent spinning on locks and barriers, time lost to yielding, interference between threads in the last-level cache and in the main memory subsystem, cache coherency traffic, imbalance between the work given to each thread, and the overhead of parallelisation itself. \texttt{perf} reports distinguishable traces of individual causes. Because each sample is attributed to the function executing when it is taken, time lost to synchronisation appears as cycles inside the routine that takes the lock or performs the atomic update, rather than as time missing from the total. Interference in the shared cache and in memory appears in the fill and miss counters of the level concerned, which can be compared between a run on one thread and a run on many. Imbalance appears in neither, and is instead visible in the difference between the two measures: a thread that has run out of work retires no cycles, so idle time lengthens the wall time of a phase while leaving its cycle count unchanged. Coherency traffic and parallelisation overhead are not separated in this thesis.
